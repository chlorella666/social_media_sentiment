# 阶段一复盘：接入真实采集数据

> 2026-08-06 | 对应提交：`c0d37db` ~ 最新

## 一、目标与结果

把应用从"演示数据"推进到**四渠道真实采集可用**：B站 / WebSearch（全网+知乎+贴吧+TapTap）
/ 微博 / 小红书，覆盖采集 → 清洗 → 情感编码（词典+LLM）→ 报告全链路，并经过四轮验收
（v1~v4）与三轮用户反馈整改。

## 二、关键举措

| 领域 | 举措 |
|------|------|
| 渠道 | B站公开 API；WebSearch 360+Bing 兜底+质量校验；微博 hotflow 热评+楼中楼；小红书 opencli Chrome 会话；知乎并入 WebSearch |
| 清洗 | 官网双过滤（标题启发式+域名黑名单）、样板/相关性/最短长度过滤、去重空键修复、丢弃原因记录、丢弃率>15%自动补采 |
| 情感 | 词典 V2（精选网络词+ECSD 电商词）、否定翻转计数、语境词排除表、反讽降置信、LLM 阈值 0.8（送 LLM 占比 69.5%）、LLM 非法值防御 |
| 数据 | 时间规范化（昨天/X分钟前→yyyy-mm-dd）、时间范围用户可选、热评+楼中楼纳入分析 |
| 输出 | Excel 5 sheet（含评论明细/丢弃明细/采集漏斗/关键词效果/LLM费用）、中文映射、HTML 报告可信度标注 |
| 产品 | 按渠道条数上限+每帖评论上限+预计耗时与费用、渠道体检、Cookie 弹窗重粘+DPAPI 持久化、WebSearch 评价后缀、LLM 相关性复核可选开关 |

## 三、做得好的方面

1. **风险前置**：小红书作为最大不确定项，用 spike 先行实测（Node/opencli/Chrome 会话），
   失败路径与解锁条件提前明确，而不是最后才碰。
2. **数据驱动**：每个改动都有基准数字（词典升级 57.8%→74.4%→90%→91.6%、阈值调整
   送 LLM 占比 45.1%→69.5%），决策可验证、可回退。
3. **防御式编程**：LLM 非法情感值（mixed）、非法叙事值（unclear）、Cookie 过期返回
   非 JSON 等边界情况均做了兜底，不中断主流程。
4. **安全习惯**：API Key/Cookie 不入库（.gitignore），Cookie 默认仅会话、可选 DPAPI
   加密；风控提醒前置。
5. **文档与代码同步**：项目方案、渠道验收矩阵随每个改动更新，决策可追溯。
6. **面向小白**：Cookie 获取图文指南、按渠道控制采集量、预计耗时/费用、渠道体检、
   官方域名配置，都在向导内完成。

## 四、遗留与下一步（供阶段二/三参考）

- 小红书楼中楼依赖 opencli 接口（当前仅顶层评论）。
- websearch 纯品牌词丢弃率仍可能 >15%（数据源官网/壳页面占比高），
  已通过评价后缀与补采缓解，关键词效果反馈可指导进一步优化。
- 抖音渠道未接入，建议 V2 明确优先级（目标平台含抖音）。
- 单次分析同步执行，关页面即中断；V2 引入后台任务队列。
- 本地轻量模型替换词典预筛（阶段二建议 A）可显著降低 LLM 费用。
- 验收脚本已固化：`python tests/manual_acceptance.py`。
