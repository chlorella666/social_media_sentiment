## 一、背景与问题

测试用户（DL）反馈：报告中的“代表词”与“词云”为**单词级词频**，无法表达完整观点，业务指向性差。

数据实证（小米任务）：

- “比想象中好”被拆成 `想象 / 中好 / 推荐`；
- “双十一当天首发下单”被拆成 `双十 / 当天 / 下单 / 首发`；
- “质量堪忧 / 后悔入手”被拆成 `质量 / 堪忧`、`后悔 / 入手`；
- 同一报告中 `top_words` 出现“质量堪忧/后悔入手”等**完整短语**，而词云是碎词 → **口径不一致**，影响可信度。

根因（代码确认）：

- `app/coding/tokenizer.py` 的 `segment` 仅做单词级词频统计（≥2 字单字词）；
- 词云与 `top_words` 使用不同口径（词云=单词词频，明细/代表词=另一套统计）；
- 无短语级（bigram/trigram）抽取与噪声过滤，高频泛词（“真的/很/了”）与碎片组合混入。

## 二、目标与验收标准（产品经理口径）

### 目标

1. 报告能表达**完整观点短语**（“屏幕易碎”“电池掉电快”“比想象中好”），不再碎片化；
2. 负面场景给出**可行动的指向**：维度 + 短语 + 原文佐证；
3. **口径统一**：代表词 / 词云 / 明细短语共用同一短语源。

### 验收标准

- [ ] 代表词区展示完整短语（正负各 Top N + 占比），如“清爽 64%”“屏幕易碎 5 条”；
- [ ] 词云以短语为整体渲染，短语内不再被拆散；
- [ ] 同一报告内 `top_words`、词云、代表短语三处口径一致（同源、无“列表完整、词云碎片”矛盾）；
- [ ] 负面原文 Top3 保留为完整观点入口，并标注对应短语；
- [ ] 小样本（短语不足）时回退单词级词频并明确标注“样本少，未形成短语”，不产生误导；
- [ ] 语义正确性抽检：以 32 条判例模式人工复核，短语误组率 ≤ 10%；
- [ ] **结果页同步升级**：App 结果页“高频情感词 Top20/词云”同样使用短语口径（避免“导出报告是短语、App 里仍碎词”的新分裂）；
- [ ] **短语可追溯**：每条代表短语可展开查看关联原文 Top3（HTML 折叠 / Excel“代表原文”列），用户可验证出处；
- [ ] **命名一致性**：全端统一“代表观点/短语”文案，无“代表词”旧称残留；
- [ ] **证据链闭合**：F-010 结论引用的短语必须在代表短语区可查。

## 三、技术方案（程序员口径）

### 3.1 短语抽取层（新增 `extract_phrases`）

位置：`app/coding/tokenizer.py`（或 `insights.py` 内独立函数），供词云 / 代表短语 / top_words 共用。

算法：

1. 清洗后文本 jieba 分词 → bigram / trigram 候选；
2. 过滤：
   - 去停用词 / 泛词（“的/了/很/真的/非常”等）；
   - 保留含**品牌名或维度关键词**的短语（强信号）；
   - 频次 ≥ 阈值（默认 2）；
   - **PMI ≥ 2.0**（点互信息），压制“想象/中好”这类高噪组合；
3. 定向模式抽取：**品牌/维度词 + 谓词 + 对象**（“屏幕/易碎”“电池/掉电/快”），作为代表观点候选；
4. 输出：`{phrase, count, pmi, sentiment_weights, sample_text_ids}`。
5. **计算细则（v0.2 补）**：
   - 共现窗口：以“句”为窗口统计共现（清洗后正文按句切分）；
   - PMI 平滑：频次下限 ≥2 之外使用 add-1 平滑，抑制低频组合的 PMI 高估；
   - 性能预算：全量文本超过阈值（如 2000 条）时按分块/抽样统计，报告生成不得超时（与 F-005 异步渲染约束联动）；
   - 阈值校准：PMI/频次/短语长度做成可配置常量，P0 判例集首轮校准后定稿并记录；
6. **sentiment_weights 定义（v0.2 补）**：短语情感分 = 其关联编码条目（sample_text_ids）的情感分布聚合（如 正面占比加权 = Σ(正面条目)/Σ(条目)），用于词云配色/字号与正负短语 Top N 排序；
7. **过滤分级（v0.2 补）**：
   - 按品牌分析模式（有品牌/维度信号）：保留含品牌名或维度关键词的短语（强过滤）；
   - 手动关键词模式（无品牌/维度）：退化为 频次 + PMI + 停用词 过滤，避免空结果或高频噪音；
   - “包含”判定复用相关性判定（`app/coding/cleaner.py`）的归一化 `_compact_for_match` 与别名词典 `BRAND_ALIASES`（如 LYSK），保证口径一致（修正：原文误写为 F-008）；
8. **英文/混合文本（v0.2 补）**：英文按空白分词即为词组，短语 = 窗口词串（如 “iPhone 15 Pro Max”）；PMI 对英文词对同样适用；不采用字符二元组断词。

### 3.2 词云升级为“短语云”

- 以短语为整体渲染：短语内以空格连接、**不可再拆**；
- 字号/颜色按短语情感分加权（正绿 / 负红 / 中灰，延续情感三色规范）；
- 中文字体：Windows `msyh.ttc` 渲染验证（与现有词云一致）；
- 短语限长 ≤ 8 字，超长短语换行/缩放，防溢出；
- **实现细节（v0.2 补，关键）**：wordcloud 默认按空白切词，短语内不得用空格连接输入——改用自定义连接符（下划线，如 `屏幕_易碎`）输入 wordcloud、渲染后还原为空格；或为 WordCloud 传入自定义 regexp 使整条短语作为单 token；验收以“渲染截图短语未被拆开”为准。

### 3.3 “代表词”升级为“代表短语/观点”

- 正负各取 Top N 短语 + 占比；
- 负面代表短语与“负面原文 Top3”并列展示（原文为完整观点入口）；
- 呈现结构参考“语义标签 + 占比”（如“清爽 64% / 涩感负面 41%”）。

### 3.4 口径统一

- `top_words` / 词云 / 代表短语共用 `extract_phrases` 输出；
- `positive_words` / `negative_words` / `top_content_words` **并入短语口径**（它们与词云同源，避免“短语区 vs 碎词区”新分裂）；
- **共现网络同步短语化（用户拍板）**：`cooccurrence` / `topic_clusters` 的节点与话题簇标签改用 `extract_phrases` 输出（节点=短语），避免话题簇仍是碎词；
- 删除旧“单词级词频”独立路径（或降级兜底专用），避免两套口径并存。

### 3.5 兼容与降级

- 小样本 / 短语不足 → 回退单词级词频 + 标注“样本少，未形成短语”；
- 词云图函数接口保持兼容（内部输入改短语）；
- 旧报告数据（result.json）展示兜底：短语缺失时显示原文词频，不报错；**旧数据字段本身是单词级**——读取时按旧口径展示或标注“旧版数据”，不与短语口径混排；
- **消费点同步补全（G3）**：`top_words` 改动波及 `pipeline.py` 概览文案“高频情感词：…”、`html_report.py` 高频词区、`insights.py` descriptor 与 `tests/test_report_insights.py` 断言——全部同步更新；
- **渲染层合并改（G6）**：与 F-005 同批修改 `html_report.py`/模板（异步分片 + 短语云），避免两轮大改模板。

## 一、背景与问题

测试用户（DL）反馈：词典模式（未配置 LLM API Key，属默认路径）下，报告只提供**分类统计描述**，没有可参考的分析，无法指导业务优化。

代码实证（词典模式 `insight_mode=lexicon`）：

- `app/core/evidence.py:build_findings(mode="lexicon")` 只产出事实性发现：F1 整体占比、F2..N 维度负面率；
- 每条发现的 `action = _directional_hint("lexicon")` **统一为“建议开启 LLM 精分析”**，无任何维度级归因或方向建议；
- `findings_to_conclusion` 平铺成文本；`generate_report_text` 仅概览（对象/数量/整体倾向/“负面率最高维度建议重点关注”一行）；
- `ReportBundle` 无结构化总结字段；HTML 结论区标题为“数据发现（词典模式）”。

结论：词典模式缺失“解读层”，数字堆叠无法回答“所以呢、先看哪、做什么方向”。

## 二、目标与验收标准（产品经理口径）

### 目标

1. 词典模式报告出现**解读式分析段**：重点问题 → 可能原因 → 建议方向，逐维度给出；
2. 报告新增**结构化总结区**：整体体验 / 正面反馈 / 负面反馈 / 重点问题归因 / 改进建议；
3. 报告明确**分析层级**（统计层 → 规则分析层 → LLM 深度层），并对无 Key 用户给出升级引导（与 F-007/F-011 联动）；
4. 全程**确定性、零 LLM 成本、措辞诚实**：同一数据永远同一解读；不虚构归因；小样本不推测。

### 验收标准

- [ ] 词典报告逐维度出现“可能原因 + 方向建议”（如“质量（负面率 62%，n=18）→ 可能集中在耐用性/品控相关讨论 → 建议优先排查质量类问题，结合负面原文 Top3 验证”）；
- [ ] 结构化总结区五块齐全，数字与 summary 一致（含 n 与占比）；
- [ ] 报告标注“分析层级：统计层 → 规则分析层 → LLM 深度层（当前：统计+规则）”，并给出开启 LLM 的引导文案；
- [ ] 确定性：同一数据两次运行解读文本完全一致；
- [ ] 措辞纪律：出现“必须/立即/停止”等强动作词视为缺陷；原因推测必须带“可能/或与…相关”；负面率 ≥50% 才用“问题归因”，否则用“值得关注”；
- [ ] 小样本守卫沿用：维度 n<3 不评级、不写推测；3~9 标注“样本有限”；
- [ ] **B 档三端 + 应用内结果页一致**：HTML / Excel / Word / App 结果页均能看到解读区；
- [ ] LLM 模式路径零改动（防回归）；旧 result.json 无新字段时区块隐藏（向后兼容）。

## 三、实现方案（程序员口径）

### 3.1 规则解读模块（新增 `app/coding/rule_insights.py`）

- `build_structured_summary(summary, evidence) -> dict`：
  - 输出 `{overall, positive, negative, top_issues[], improvements[]}`；
  - 全部由既有字段推导：`sentiment_distribution`、`dimensions[].negative_rate/count`、`consumer_voice`、`top_words`、`evidence`（stat / dimension:xx / 负面原文 refs_neg）；
  - **数字字段结构化存储**（negative_rate/count 单独字段，字符串仅在渲染层拼装），保证与 summary 逐字段一致；
  - **top_issues 排序复用 build_findings 的稳定排序键**（score 降序，同分按维度 id），保证确定性；
  - 纯字符串模板 + 数据插值，零新增依赖、零网络、零 LLM 调用。
- `dimension_interpretation(name, negative_rate, n, refs) -> {cause, direction}`：
  - 按“维度类型 × 负面率分档”组合原因库/建议库模板；
  - 小样本（n<3）不返回推测；`need_review` 维度附加“待复核”标注；
  - **refs_neg 为空时不输出“结合原文验证”指引**，改为“结合维度明细查看”，避免证据落空。

### 3.2 findings 扩展（`app/core/evidence.py`）

- `build_findings` 在 lexicon / fallback / review 模式的每条维度发现注入 `cause`、`direction` 字段；F1 注入整体解读；
- **review_refresh / template_fallback 模式同样产出 cause/direction**（口径与 lexicon 一致，基于复核后/兜底 summary）；
- **`rebuild_report_after_review`（复核/反馈后重算）同步重建 structured_summary**，避免旧解读残留；
- `_directional_hint` 升级为“逐维度方向建议”，不再全量复用同一句；**LLM 模式路径零改动**。

### 3.3 数据模型与组装

- `app/core/models.py`：`ReportBundle` 增加 `structured_summary: dict = Field(default_factory=dict)`（旧数据缺省空，向后兼容）；
- `app/coding/insights.py:build_report_content` 词典分支返回 `structured_summary`；
- `app/core/pipeline.py`：组装进 `ReportBundle`；`generate_report_text` 结尾追加“详细解读见『解读与建议』”一行（有解读时）；
- **结果页只读 `bundle.structured_summary`，渲染层不重算解读**（避免大数据 rerun 卡顿）。

### 3.4 呈现（B 档：三端 + 应用内结果页）

- `app/output/templates/report.html.j2`：
  - 词典模式新增“📊 解读与建议”区块（结构化总结五块 + 逐维度原因/方向）；
  - 结论区标题升级为“数据发现与解读（词典模式）”；
  - 报告开头/结论区增加“分析层级”说明条（统计层 → 规则分析层 → LLM 深度层）；
- `app/output/excel_writer.py`：新增“解读与建议”工作表；
- `app/output/word_report.py`：同步渲染结构化总结；
- `app/ui/results.py`：词典模式结果页 findings 区下方新增“解读与建议”折叠区（B 档），与 HTML 同源；
- 解读区顶部“一句话结论”胶囊（复用 lead/overall），先结论后细节；
- 逐维度“语义标签+占比”用**占比条可视化**（HTML/App 端 CSS），对齐 CEMPRO 参考形态；
- 每条“可能原因”附“查看原文（负面 Top3）”折叠（evidence refs_neg），形成解读→证据闭环；
- **“事实 vs 推测”视觉区分**：数据（占比/n）正体，推测斜体/虚框 + “可能”前缀高亮；解读区角标/折叠说明“原因基于统计特征的规则推测，非 AI 归因，请结合原文验证”；
- “分析层级”说明条**正向措辞**（“当前：统计+规则解读（零成本）；开启 LLM 解锁：可归因深度分析 / 行动建议 / 短语级洞察”），与 F-011 联动提供“去配置”入口；
- 长维度名截断+悬浮全文；HTML（Jinja 转义）/ Word / Excel 统一转义。

### 3.5 规则库设计（文案组件化，集中维护）

- 原因库：按“维度类型 × 负面率分档（高 ≥60% / 中 40~60% / 低 <40% 但有 n）”生成“可能原因”；
- 建议库：优先排查维度 → 结合负面原文 Top3 验证 → 扩大采集 → 开启 LLM 深度归因（F-007/F-011 联动文案）；
- 措辞纪律（写进单测黑名单）：禁止“必须/立即/停止”等强动作词；原因推测必须“可能/或与…相关”；负面率 ≥50% 才用“问题归因”。

### 3.6 兼容与降级

- 旧 result.json 无 `structured_summary` → 区块隐藏，不影响渲染；
- 零数据短路（`no_data`）不变；
- **F-009 联动（G2 修正，v0.1.9 同批落地）**：解读输入 = evidence 负面原文 Top3（refs_neg，完整句子）+ **`top_phrases`（F-009 输出）** + 维度明细；**不直接引用 `top_words`（碎词源）**；原文 Top3 保留为证据闭环入口；
- **极端数据降级**：total 1~9 / 全中性 / 负面率=0 / consumer_voice 或 top_words 缺失 / refs_neg 为空时，解读区退化为“仅统计层”并隐藏推测（不输出原因/方向）。

- 红框核心分析文本：**逐特征给正/负面占比**——“清爽感 64% 正面（最受欢迎）；甜度/酸甜度正面较高；涩感/苦味负面突出（41%/36%）；余味/香味正面偏低”→ 整体情绪占比（正面 34.29 / 中性 35.36 / 负面 30.36）→ **前瞻性建议**（聚焦提升涩感苦味平衡、加强余味香味优化）；
- 图表：NSR 环形图 + “口味指标提及”Treemap（每块=特征名+提及数，如清爽感 135、甜度 128、涩感 66、苦味 47）。

**参考材料3（VOC 报告“总结”页 · 结构化总结形态）**

- 结构：**① 客户体验整体总结**（正面 78.38%（892 条）+ 领域明细；服务改进=低分领域及原因；特别关注客户；客户原声；综合来看）→ **② 客户原声提炼总结：重点问题 → 形成原因 → 客户期望**，每条带占比，原因措辞为“形成原因：**可能由于…**”。

### 7.2 与 F-010 方案的对应

1. **解读式分析段**：按材料 2 形态实现——“总述多样性 → 逐维度/特征语义标签+占比 → 整体情绪占比 → 前瞻方向建议（保守措辞）”；

3. “语义标签+占比”作为解读区辅助清单形态；Treemap 提及量列为后续（F-009 短语云）兄弟增强，F-010 本轮不做图；
4. 材料 3 的“形成原因：可能由于…”印证本方案“不虚构归因、措辞保守（可能/或与…相关）”的纪律符合行业范式。

## 一、背景与问题

测试用户（DL）反馈：**开了 LLM 但实际没用上**（未配置 API Key → 全程词典模式），且微博 Cookie 输入框同样容易被忽略，判定为**全局 UX 问题**：需要用户填写的“凭据类”输入框缺少视觉引导，小白易漏填。

根因（代码确认）：

- `app/ui/sidebar.py`：API Key 为 `st.text_input("API Key（可选）", type="password", key="api_key_input", ...)`，文案含“（可选）”弱化必要性，视觉与普通输入框无差别，且仅在“启用 LLM 精分析”展开后才出现；
- `app/ui/wizard.py`：微博 Cookie 为 `st.text_input("微博 Cookie（粘贴已登录的 Cookie）", ...)`（②渠道页右侧列），无强调样式，也未在提交前说明“不填该渠道会失败”；
- 全局无统一的“凭据/必填”样式体系：`app/ui/global.css` 只有通用输入框 focus 样式；
- 提交前校验不足：LLM 无 Key 仅普通 `st.warning`（确认页红色 error 由本方案归口负责，F-007 只负责 need_review 展示口径——M4 归口）；微博无 Cookie 时**无前置拦截**，任务提交后由采集层失败/降级，用户白跑；
- 缺少“配置未完成”常驻状态与“已配置 ✓”的确认反馈；
- **补充（v0.2）**：仅判“有没有”不够——“已配置 ✓”≠“可用”（错误 Key / 过期 Cookie 仍显示绿色），需补“是否可用”的验证与反馈。

## 二、目标与验收标准（产品经理口径）

### 目标

1. 凭据类输入框（API Key / 微博 Cookie）**一眼可识别**：强调分组 + 前置图标 + 明确文案（去掉“可选”歧义）；

## 三、技术方案（程序员口径）

### 3.1 凭据区强调（双方案，避免 aria-label 依赖）

定位机制（v0.2 修订）：**首选容器强调分组，CSS aria-label 仅作兜底**，避免 Streamlit DOM 漂移导致静默失效。

1. **首选：`st.container(border=True)` 强调分组**（Streamlit 1.6x 支持）：
   - API Key、微博 Cookie 输入框分别包进带边框容器，容器内顶部渲染强调标题（图标 + 文案 + 后果一句话）；
   - 容器边框/底色走 `global.css` 统一凭据样式（`.credential-box` 类可通过 `st.markdown` 注入的 CSS 命中容器 data-testid 组合，或直接依赖 container 默认边框 + 前置标题，不写脆选择器）；
2. **兜底：CSS 高亮输入框本身**（若 1.62 DOM 证实 `input[aria-label]` 存在则启用，否则跳过）：

```css
/* F-011：凭据输入框高亮（兜底；依赖 Streamlit DOM aria-label） */
div[data-testid="stTextInput"]:has(input[aria-label*="API Key"]) input,
div[data-testid="stTextInput"]:has(input[aria-label*="微博 Cookie"]) input {
  border: 2px solid var(--s-warning-border, #D9A400);
  background: var(--g-50, #FFFDF5);
  font-weight: 600;
}
```

3. 文案（两处 label/标题统一）：`🔑 LLM API Key（填写才能启用精分析；不填则词典模式）`、`🔐 微博 Cookie（该渠道采集必需）`；
4. 新 CSS 进 `global.css` 时遵守项目已知约束：压缩单行、无字面 `</style>`、`:has()` 在旧 Edge 不支持时“无高亮但不坏功能”。

### 3.2 配置中心状态区（sidebar）

- 侧边栏新增“配置中心（LLM / 微博 / Node / opencli）”区（Node/opencli 状态行并入本区，见 §四 F-012 3.3），逐项读取 `load_api_key` / `load_cookie("weibo")` / `node_ready` / opencli 状态与会话值，实时渲染：
  - 已配置且验证通过：`✅ LLM API Key：已配置（尾号 ****1234）`；
  - 已配置未验证：`⚠️ 已配置，未验证 —— 建议「测试连接」`；
  - 未配置：`⚠️ LLM API Key：未配置 —— 开启 LLM 将自动降级词典模式`；
- **可用性判定（v0.2 新增）**：
  - 保存时提供“保存并测试连接”选项（复用现有测试连接逻辑），测试结果写入 session（通过→绿；失败→红 + 错误摘要）；
  - 微博：`health` 探测或“采集失败（Cookie 失效）”事件回写状态区；
  - env 探测：`load_api_key(allow_env=True)` 命中时显示“已检测到环境变量配置”（开发场景，不误报未配置）；
  - 平台/权限：macOS 显示“明文 0600 存储，更建议临时粘贴”；secrets 写失败捕获并提示“保存失败（权限/只读目录）”；
- 状态判定函数集中到 `app/core/config_status.py`（新增）或 `app/core/secrets.py`，sidebar/wizard/results 三处共用，避免口径漂移；**只读复用 secrets/health/jobs，不新增写路径，避免依赖环（G6）**；微博“校验”用懒触发按钮，不做每帧自动网络探测（G6）；
- 不显示明文（尾号脱敏）；读取失败按“未配置”处理并附“读取失败”提示。

### 3.3 ②渠道页微博行警示 + 向导级状态

- 微博被选中且无 Cookie（会话 + secrets 均无）时，输入框上方黄色警示条：“未配置微博 Cookie：该渠道采集会失败。请按下方 5 步获取（Application/Storage 路径），或取消勾选微博。”；
- 配置后警示条实时消失；输入框按 3.1 强调分组；
- 微博 Cookie 输入框下方提供“🔍 校验 Cookie 是否有效”小按钮（可选，复用 health 探测），增强信心。

### 3.4 提交前强校验（确认页）

- **语义差异显式化（v0.3 修订）**：
  - LLM 开启无 Key → 红色 `st.error` + 摘要行标注“开（未配置 Key → 降级词典）”，**不阻断提交**（词典模式是合法降级；此提示归口本方案，F-007 仅负责 need_review 展示区分——M4）；
  - 选微博无 Cookie → 红色 `st.error` + **默认阻断提交**（必败），逃生口需**二次确认**：勾选“我了解该渠道会失败，仍要提交”后才放行；
- 阻断用现有 `st.stop()` 模式，逃生口按钮/勾选必须渲染在 `st.stop()` **之前**，否则不可达；
  - **与 demo-only 勾选互斥（G5）**：微博阻断逃生口与“我确认本次只跑演示数据”使用独立 key，多条件校验互斥；`tests/test_ui_flow.py` 提交路径同步更新；
- 校验逻辑收敛到“配置状态”判定函数（3.2），供确认页与后续版本复用。

### 3.5 与 F-007 / F-010 联动

- 词典降级 banner、无深度分析提示统一文案前缀“配置中心：”；
- F-010 规则分析层上线后，其“词典模式解读段”顶部同时展示“配置中心：未填 API Key → 无 LLM 深度分析”提示；

- **依赖排期（v0.2）**：F-010 文案未定稿前，“联动文案”先留占位，避免返工。

### 3.6 测试

- 单元/AppTest：
  - 状态区：无 Key 未配置 / 保存后已配置（尾号脱敏）/ env 命中不误报 / secrets 读取失败兜底；

## 四、风险与对策

| 风险 | 对策 |
|---|---|
| Streamlit DOM/aria-label 结构随版本变化，CSS 定位失效 | 首选容器强调分组（不依赖 aria-label）；CSS 兜底仅视觉；升级后回归 + 浏览器走查 |
| `:has()` 在旧 Edge 不支持 | 高亮静默降级为“无强调但功能正常”；分组容器不依赖 `:has()` |
| “必填”措辞误伤“故意不开 LLM 跑词典”的用户 | 校验仅当 LLM **已开启** 或微博 **已选中** 时触发；文案精确表述降级路径 |
| 微博阻断导致无法“明知会失败仍提交” | 逃生口二次确认（勾选“我了解会失败”），默认阻断但可显式覆盖 |

## 四、F-012 专项：一键安装 Node.js / opencli（winget 版本兼容与安装体验）

> 来源：由问题清单 F-012 升格为专项；与 F-009/F-010/F-011 同批组成 v0.1.9 专项四件套，并与 F-011 合并改 ②渠道页/配置中心（避免两轮改同一 UI 区）。
> 登记：[便携版试用反馈问题清单.md](便携版试用反馈问题清单.md) F-012

### 一、背景与问题

测试用户（DL）点击「安装 Node.js」报“执行失败（退出码 2316632066）：当前命令无法识别参数名称:1--disable”（winget v1.2.1069）。

根因（代码确认）：`app/channels/health.py::install_node_winget` 固定传参 `--disable-interactivity`——该参数需 winget ≥1.6；旧版 winget 不识别导致解析失败、安装中止。子进程为列表直传，参数未被拼坏（“1--disable”是 winget 自身解析提示）。

该功能是**小红书 opencli 一键安装的前置链路**；失败会让“想用小红书”的小白卡在入口（首轮虽不引导，但进阶必用）。

### 二、目标与验收（产品经理口径）

目标：
1. 不同 winget 版本（新/旧）都能成功或给出**明确可执行指引**，不再以“执行失败”结束；
2. 安装过程/结果反馈清晰（进行中 / 成功 + 下一步 / 失败 + 原因 + 动作）；
3. 与 opencli 安装、F-011 配置中心联动，形成“Node → opencli → 使用小红书”完整链路。

验收：
- [ ] 新/旧 winget 环境各冒烟一次：新 winget 静默安装成功；旧 winget 不再报参数错误（走兼容路径或给出“更新应用安装程序 / 手动下载”指引）；
- [ ] 失败按原因分类并给出下一步（winget 缺失 / 版本过旧 / 源或网络 / 权限 / 未知）；
- [ ] Node 已安装检测（PATH + 常见路径）后按钮显示“已安装（版本 xx）”，不重复安装；
- [ ] Node 未装时点「一键安装 opencli」→ 拦截提示“请先安装 Node.js”（或链式先装 Node）；
- [ ] 安装状态写入 F-011 配置中心（Node / opencli 两行：已装版本 / 未装 + 后果）；
- [ ] macOS 分支：brew 缺失给出手动指引；装好后提示重启终端；
- [ ] 全量回归 38/38 + 黄金集 PASS；包内 AppTest 冒烟（②页按钮状态与拦截）。

### 三、技术方案（程序员口径）

3.1 winget 兼容（核心修复）
- 去掉固定 `--disable-interactivity`，或按版本探测附加：
  - 推荐实现：先去掉该参数（`--silent` 已足够静默，OpenJS.NodeJS.LTS 安装无额外交互），简单稳妥；若需保留静默强化，再按 `winget --version` 主版本 ≥1.6 才附加；
- 同时按版本附加 `--accept-source-agreements` / `--accept-package-agreements`（旧版不支持则不传），并为整体安装加超时保护（如 120s 无输出判超时），防止隐藏窗口内源协议/许可弹窗挂起；
- 验收以“旧 winget 不再报参数错误”为准。

3.2 失败分类与指引
- 分类逻辑集中 `health.py`（`_classify_winget_error`），返回结构化 `{ok, reason, guide}`：
  - winget 不存在 → “需 Windows 10/11，请到 https://nodejs.org 手动下载”（已有）；
  - 输出含“无法识别参数名称” → “winget 版本过旧：请到 Microsoft Store 更新「应用安装程序」，或手动下载 Node.js”；
  - 源/网络类（连接失败、超时、winget 报源不可用） → “网络/源不可用，请重试或手动下载”；
- **退出码分类边界（重要）**：0x8A15xxxx 是 winget 安装器错误区间（如 0x8A150002 常见为安装器内部/清单错误），**不能仅按码段归为网络**——分类以输出文本关键词优先，各分类用真实 winget 输出 fixture 校准后再定稿；
  - 权限类（拒绝访问/需管理员） → “请以管理员身份运行后重试，或手动安装”；
  - 其他 → 展示输出尾部 + 手动下载链接。

3.3 UX 增强（并入交付）
- 安装进行中：spinner + 流式输出行，不假死（复用 `_run_streaming` 的 on_output）；
- 成功：绿 ✓ + “请重启应用后再点「安装 opencli」”（明确下一步）；
- 失败：红 ✗ + 原因分类 + “打开手动下载页”/“复制错误信息”（`st.code` 可复制）；
- Node 已就绪：按钮禁用并显示版本，或变为“打开 opencli 安装”；
- F-011 配置中心新增 Node / opencli 状态行（只读展示，点击直达安装入口）；
- 安装为**系统级软件安装**，UI 明示“将安装系统级软件（winget/npm）”，避免无感知；
- macOS：brew 缺失提示；装完提示重启终端/应用；
- **成功自检**：安装完成后自动 `node --version` / `opencli --version` 验证，并把真实版本写入配置中心状态行；
- **免重启链式安装（UX 加分项）**：Node 装完后不要求用户重启整个应用——用新子进程或重读用户环境变量（如 `[Environment]::GetEnvironmentVariable('Path','User')`）让应用感知新 PATH，直接提供「继续安装 opencli」按钮；若实现复杂度高，退化为「检测 Node 就绪并继续」按钮（内部用新进程探测）；
- 手动下载指引注明“安装时勾选 Add to PATH”（小白常见失败点）；
- 安装日志落盘（并入 `launcher.log` 或独立 `install.log`，对齐 F-004 留痕规范）；失败时错误信息用 `st.code` 展示并可复制；
- winget 触发 UAC 提权时隐藏窗口内无法交互——检测到需提权时引导“右键以管理员身份重新运行启动脚本后重试”。

3.4 opencli 联动
- Node 未装时点「一键安装 opencli」→ 拦截“请先安装 Node.js”（或链式先装 Node 再装 opencli）；
- opencli 安装失败（npm 网络/镜像）→ 回显输出 + 手动命令指引（保留现有 `use_mirror` 走 npmmirror）；
- opencli 安装成功 → 配置中心 opencli 行转绿 + “重新打开小红书渠道页”提示。

3.5 测试
- 单测：参数构造（新/旧 winget 分支）、`_classify_winget_error` 各分类、`node_ready` 判定；
- AppTest：②渠道页 Node/opencli 按钮状态与拦截提示；
- 全量回归 38/38 + 黄金集；包内冒烟（mock winget 输出验证分类与引导）。
