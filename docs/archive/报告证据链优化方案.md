# 报告证据链优化方案（结论可追溯 · 建议可执行 · 含无 LLM 分支）

> 创建：2026-08-18 | 状态：**已执行（v0.20.0，2026-08-18，回归 32/32 全绿）**；
> 待人工验收（四份样本对照 §2.2 六条，验收工具 scripts/regen_report.py）
> 对象：用户侧社媒情感分析报告（HTML / Word / App 结果页三端）
> 关联：2.11 需复核样本闭环（need_review 剔除/标注）、2.8 全量 LLM 路由（证据更全）、
> 评测中心 n<30 纪律（本方案沿用其小样本守卫口径）

## 一、问题定义：报告"泛泛而谈"的本质

用户读报告时要能回答三个问题：**最大的问题是什么？证据是什么？我该做什么？**
现状报告没有完成这个任务——数字很多，但结论和证据是断开的。

### 1.1 七个病灶（均来自真实报告，2026-08-15~16 运行）

| # | 病灶 | 真实案例 | 代码位置 |
|---|---|---|---|
| A | 概览是固定模板，结尾万能句 | 苹果/TCL/罗技/vivo/OPPO/惠普的概览逐字相似，结尾全是"扩大采集范围后复测以验证趋势" | `pipeline.generate_report_text` |
| B | LLM 建议是通用公关模板，品牌间可互换 | TCL 与 OPPO 的"行动建议"除了数字几乎一样（竞品对标/质检报告/KOL/预警机制） | `llm_analyzer.generate_insights` prompt |
| C | 结论无原文引用，证据数据其实都在 | 罗技"渠道服务负面率 100%"实为 3 条微博（8/12 假货/贴牌、7/30 罚款），报告只给百分比 | `insights.build_descriptors` 只传聚合数字 |
| D | 小样本照常下大结论，n 守卫缺失 | TCL 结论写"B站设计与做工负面率 100%"——实际该格 n=1 | descriptors/LLM 均无 n 守卫 |
| E | 模板兜底结论与数据脱节甚至相反 | 小米手机负面 30.4% > 正面 17.4%，兜底结论却说"整体舆论以中性/正面为主" | `insights.template_insights` 静态文本 |
| F | 零数据也调 LLM，产出整段幻觉 | 安克 0 帖 0 文本，LLM 推断"存在采集问题、应延长监测 30 天、培训团队" | `pipeline` 对 0 样本仍调 `build_insights` |
| G | 高频词/负面话题词与结论脱节 | OPPO `sentiment_sources` 有"后台 80%""系统 71%"，结论未引用；TCL top_words 大量归因词未用 | 结论区不读取 `sentiment_sources`/`top_words` 证据 |

### 1.2 根因（一句话）

报告生成是"统计数字 → LLM/模板解读"的**单层结构**：没有证据抽取层，LLM 只能看到
聚合描述（还是无 n 守卫的描述），自然退化成通用话术；结论区 prompt 强制"五种叙事
框架必写"进一步逼出填充文字；静态模板兜底和零数据分支也没有守卫。

## 二、目标与成功标准

### 2.1 目标

报告从"数据汇报"升级为"决策材料"：**每条结论可 3 步内追溯到原文+平台+日期；
每条建议包含动作/对象/渠道并挂到具体发现；小样本与低精度判定不越权下结论。**

### 2.2 验收标准（6 条，全部满足才算达标）

1. 任意结论行都能追溯到"原文 + 平台 + 日期"（人工抽查 ≥3 条）；
2. 任意行动建议（LLM 模式）都包含"动作 + 对象 + 渠道"且挂到具体发现编号，
   无"发布质检报告"这类无主语、无对象、无依据的建议；
3. 报告中不存在 n<3 却表述为"100%/最差/最高"的断言；
4. 零数据任务不出现任何"推断/建议"类内容；
5. 三端（HTML / Word / App 结果页）展示一致，旧报告（无新字段）降级显示不报错；
6. **无 LLM 报告专属**：结论全部数据驱动（含真实数字与 n 标注）；每条证据标注
   "词典判定 · 仅供参考"；不出现危机公关/质检报告/促销策略类强动作建议；
   有"开启 LLM 精分析"升级提示；负面占比高于正面时绝不允许出现"中性/正面为主"。

验收样本：3 份有 LLM 真实报告（罗技 / TCL / OPPO）+ 1 份无 LLM 报告（筛选自测），
重新生成后人工对照评审。

## 三、总体架构：报告加"证据层"

```text
coded_items + summary + schema
              │
              ▼
  evidence.py（规则层，确定性、可回归）
  ├─ 证据级联：LLM 维度情感 → 词典维度情感 → 整条情感×维度关键词
  │            → 话题词反查 → 整体负面文本 TOP
  ├─ 降噪：脏话过滤 / PII 脱敏 / 截断 / need_review 剔除或标注
  └─ 守卫：n<3 不评级、零数据短路、广告内容剔除
              │
              ▼
  findings 生成器（双模式，共用一套规则内核）
  ├─ mode=llm：LLM 在给定证据上写"发现驱动"解读（P1.5）
  └─ mode=lexicon / llm 失败兜底：规则生成事实性发现 + 方向性提示（P0 起就位）
              │
              ▼
  渲染层：HTML / Word / App 结果页（三端一致）+ 词典模式 banner
```

设计原则：
- **证据由规则抽取，LLM 只解读不选材**——防止幻觉引文；
- **一套规则内核两个入口**（无 LLM 默认 / LLM 失败兜底），比现在的双套逻辑更简单；
- **向后兼容**：ReportBundle 新增字段可空，旧 result.json 降级显示。

## 四、数据层与 schema（新增字段均可空，向后兼容）

`ReportBundle` 新增：

```jsonc
{
  "findings": [                        // 结论区数据源（LLM 或规则生成）
    {
      "id": "F1",
      "claim": "渠道服务负面集中在假货/贴牌吐槽（微博，8 月中旬）",
      "evidence_refs": ["E2", "E3"],
      "action": "无 LLM 模式下为空或方向性提示；LLM 模式为可执行建议",
      "narrative_label": "attribution: enterprise"   // 可选，叙事框架降级为标签
    }
  ],
  "evidence": [                        // 证据卡数据源（规则抽取）
    {
      "id": "E2",
      "text": "中招了.换鼠标…包装都没有罗技字样…",   // 截断 ≤80 字
      "platform": "weibo",
      "date": "2026-08-12",
      "keyword": "罗技",
      "dimension": "channel_service",
      "sentiment": "negative",
      "judge": "llm",                  // llm | lexicon
      "need_review": false,
      "n": 3                           // 该维度×该判定下的样本数
    }
  ],
  "insight_mode": "llm"                // llm | lexicon | template_fallback
}
```

渲染规则：`findings`/`evidence` 为空 → 隐藏新区块，旧报告不报错。

## 五、分优先级执行

### P0 修错（0.5~1 天，零新增 LLM 费用，优先级最高）

| 改动 | 说明 | 解决病灶 |
|---|---|---|
| 零数据短路 | `total_items==0` 时不调 `build_insights`，直接渲染"数据不足"固定区块（含建议调整关键词/渠道，不含推断） | F |
| n 守卫 | `build_descriptors`：`count<3` 的维度/平台×维度/日期×维度格子不输出百分比、不参与"最差/最高"评选，描述加"（样本不足）" | D |
| 概览去万能句 | `generate_report_text` 结尾改为真实 top 负面话题词（`sentiment_sources`，n≥3 才进榜），并指向发现编号 | A、G |
| 模板兜底数据化 | 删除静态"整体舆论以中性/正面为主"；模板兜底改为规则 findings 生成器（真实 worst_dim + n + top 负面词 + 方向性提示）；`insight_mode` 标注兜底来源 | E |

P0 落地点：
- `app/core/pipeline.py`：零数据短路 + 传 schema 给 evidence 层；
- `app/coding/insights.py`：`template_insights` 重写为数据驱动；`build_descriptors` 加 n 守卫；
- `app/core/models.py`：ReportBundle 新字段；
- `app/coding/llm_analyzer.py`：`generate_insights` 失败时返回规则 findings 而非旧模板。

### P1 证据链（1~1.5 天，规则实现，无新增 LLM）

1. **新增 `app/core/evidence.py`**：
   - 证据级联（见 §三）；每维度 top 证据选择规则：负面优先（情感分 × 强度 × 新颖度），
     去重、每维度 ≤3~5 条、每条含平台/日期/关键词/n；
   - 降噪：脏话词过滤（替换为"原文含粗口，已略"）、复用 `desensitize_text` 脱敏、
     截断 ≤80 字、`need_review` 文本剔除或标"待复核"、广告内容剔除；
   - 守卫：n<3 不评级、零数据返回空。
2. **三端渲染**：HTML / Word / App 结果页新增"核心发现"证据卡区块
   （每条 = 结论一句话 + 数字 + 原文引用 + 平台/日期，默认折叠，可展开）+ 
   维度分析区每维度"负面原文 TOP 3"。
3. **词典模式 banner**：HTML/Word/App 三端固定提示"本次为词典模式，维度情感与
   结论仅供参考；开启 LLM 精分析可获得可归因的结论与行动建议"；每条证据标注
   判定来源（`llm` / `lexicon · 仅供参考`）。

### P1.5 结论区结构改造（0.5~1 天，LLM 模式，改一次现有调用，费用不变）

- prompt 从"按五种叙事框架必写 300~500 字"改为**"发现驱动"**：最多 5 条发现，
  每条 = 结论一句话 + 证据引用（必须来自给定证据清单）+ 一条可执行建议
  （动作 + 对象 + 渠道 + 发现编号）；
- 叙事框架降级为**每条发现的归因视角标签**（可选），不再强制五框架全写；
- 输入 descriptors 附带证据清单（含 ref id 与 n）；输出 `{findings: [...]}`，
  JSON 解析失败 → 规则 findings 兜底。

### P2 结构化 findings 与引用校验（本次暂缓）

后端校验 conclusion 引用必须来自证据集、findings 落库。**价值确定但工程量最大，
建议先看 P1.5 实际效果再决定**，避免过度设计。

## 六、无 LLM 分支（用户已确认：保留方向性提示）

### 6.1 现状

无 LLM（`plan.llm_enabled=False`）：全部词典判定、无叙事归因、洞察落静态模板
（病灶 E 的最严重受众）、概览万能句。维度级情感**有词典轻量版
`match_dimension_sentiments`**（`app/coding/dimensions.py`，分句打分，确定性可回归），
任务选了领域 schema 即填充；无 schema 则为空。

### 6.2 无 LLM 模式的行为（与 LLM 模式的差异）

| 维度 | 无 LLM 模式 | 有 LLM 模式 |
|---|---|---|
| 证据来源 | 词典维度情感 → 整条词典情感×维度关键词 → 话题词反查 → 整体负面文本 TOP | LLM 维度情感优先，同链路回退 |
| 证据标注 | 每条标"词典判定 · 仅供参考"；need_review 文本剔除 | 标"LLM 判定"；need_review 标"待复核" |
| 结论 | 规则生成**事实性发现**（数字 + n + 原文指向） | LLM 生成发现 + 可执行建议 |
| 建议 | **方向性提示**：如"负面集中在渠道服务相关讨论（n=3，样本不足），建议开启 LLM 精分析获取可归因结论后再制定具体行动"；**不给**"立即危机公关/质检报告/促销策略"类强动作建议 | 可执行建议（动作+对象+渠道+发现编号） |
| banner | "本次为词典模式，维度情感与结论仅供参考；开启 LLM 精分析可获得可归因的结论与行动建议" | 无（或仅 LLM 失败兜底时提示"模板兜底"） |

### 6.3 工程要点

- `build_insights` 按 analyzer 类型分支：MockAnalyzer → 直接走规则 findings
  （**不再尝试 LLM、不再落静态模板**）；
- 规则 findings 生成器输入 `(evidence, summary, mode=lexicon)`，输出事实性发现 +
  方向性提示（模板带真实数字与 n）；
- 无 schema / 无维度时：跳过维度级证据，回退"整体负面文本 TOP"并标注
  "未启用维度分析"（与现有 `dimension_note` 对齐）。

## 九、风险与不撞车

### 风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| LLM 仍写泛建议 | 中 | 结论区仍泛 | prompt 正反例 + 规则校验（建议必须带动作/对象/渠道/发现编号），不过则降级规则生成 |
| 证据卡信息过载 | 中 | 小白读不动 | 默认折叠原文，只显示结论行 |
| 原文含脏话/个人信息 | 中 | 品牌方尴尬/泄露 | 脏话过滤（"原文含粗口，已略"）+ 复用脱敏 + 截断 ≤80 字 |
| 词典模式证据误判 | 高（已知短板） | 误导归因 | 证据标"词典判定·仅供参考" + 建议收窄为方向性提示 + need_review 剔除 |
| 改动影响既有报告测试 | 中 | 回归红 | 更新断言 + 新增用例，纳入一键回归 |

### 不撞车

| 在途项 | 关系 |
|---|---|
| 2.8 自定义维度 + 全量 LLM | 只读其产出（coded_items/schema）；全量 LLM 反而让 LLM 分支证据覆盖更高，顺风车 |
| 2.11 需复核闭环 | 读取 need_review 标记，不改其流程 |
| 其他渠道关键词策略方案（B站/微博/小红书） | 纯采集层，无交集 |
| 2.10 WebSearch 评论抓取 spike | 纯采集预研，无交集 |
| 评测中心审视报告 | 独立专项；仅复用其 n<30 小样本纪律口径 |

### 2026-08-18 执行记录（v0.20.0）

按执行前评审补充的 8 项修订落地：

1. **离线验收路径**：新增 `scripts/regen_report.py`（从 result.json 重建报告阶段，
   不重新采集；WebSearch 风控时验收不被卡死）；

### 2026-08-18 修订（验收中发现：LLM 模式大面积误降级）

**现象**：验收样本罗技/OPPO 用 `--llm` 重建时 `insight_mode = template_fallback`
（2/3 误降级），TCL 正常；诊断确认 LLM 实际输出质量正常（解析成功、引用合法、
action 含动作/对象/渠道），但 `validate_llm_findings` 整组判 False。

**根因**：校验规则要求 action 正文必须出现发现编号（F#）或证据编号（E#），
而真实 LLM 输出通常省略编号（编号挂接已由 JSON 结构天然满足）→ 整组误杀降级。

**修复**（[evidence.py](../app/core/evidence.py) + [insights.py](../app/coding/insights.py)）：
1. 校验放宽：action 长度 ≥12 且含具体渠道/平台标记（微博/B站/知乎/小红书/京东/
   渠道/平台等）或引用 F#/E# 即通过；证据引用存在性与 ≤5 条保持硬校验；
2. 按条过滤（`filter_llm_findings`）：坏条只丢自己，不连累整组；
   全部非法才整组回退规则 findings；
3. prompt 强化：action 须含具体渠道并建议末尾注（对应F#），附正例；
4. 规则 findings 措辞修正：负面率 <50% 时改"负面讨论涉及…话题"，
   不再一律"负面集中在…"（避免过度断言）。

**回归**：test_evidence 扩 3 项（放宽校验/按条过滤/部分降级），
全量回归 32/32 全绿 + 黄金集门槛 PASS。

### 2026-08-18 修订 2（人工验收发现：统计类结论引用单条原文有偏差）

**现象**：抽查发现"强情绪占比 43%""情感走势下降（均分 0.156→0.064）"
"品牌形象负面率 80%"等**统计/聚合类结论**被挂到单条原文上——单条文本
支撑不了聚合数字，造成"引用有偏差"。

**根因**：证据层只有原文卡（kind=text），LLM/规则找不到"数字类证据"可引，
只能拿单条原文充数。

**修复**：
1. 新增**统计证据卡**（`kind=stat`，id 前缀 S）：整体分布 / 平台平均分 /
   维度负面率 / 走势 / 强度，共 5 类，数字与 build_summary 同口径；
2. 规则 findings 改引统计卡：整体发现 → S1；维度发现 → 维度统计卡 + 至多
   2 张原文卡作例证（不再只用原文卡）；
3. LLM prompt 强制区分：统计类结论必须引用统计卡，禁止用单条原文支撑统计
   数字；原文卡只用于具体文本现象类结论；宁可留空 refs 也不引不相关原文；
   统计卡全文始终随 prompt 给出（不受前 20 条限制）；
4. 校验新增维度/平台一致性：结论提到某维度/平台名时，引用必须含该维度/平台
   的卡（统计卡或原文卡），拦截跨主题引用；
5. 三端渲染区分：统计卡显示"📊 统计：…（来源：报告统计）"，不再伪装成原文。

**边界**：证据卡"维度标签与文本不符"（如 OPPO 样本"杀后台"文本被标为
设计与做工）属于历史任务编码数据问题，报告层不重判旧标签，新任务由 LLM
维度情感产生；验收记录中已注明。

**回归**：test_evidence/test_report_insights 更新（统计卡、一致性校验用例），
全量回归 33/33 全绿 + 黄金集门槛 PASS。
