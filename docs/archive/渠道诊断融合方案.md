# 渠道体检 × 一键探针 融合方案（渠道诊断面板）

> 状态：**已实施（2026-08-15，分两个提交 A/B）** | 关联：向导③渠道设置（`app/main.py`）、
> `app/channels/health.py`、`app/channels/websearch.py`、`app/core/jobs.py`（channel_state）

## 一、背景与问题

当前向导③有两个按钮，用户视角是同一件事——"我选的渠道现在能不能用"：

1. **渠道体检（只读探测）**（`main.py` 约 L1306 → `health.check_channel_health`）
   - 覆盖所有已选渠道；B站/微博发真实请求、小红书只查环境、WebSearch **只发 1 个
     请求且只看 HTTP 200**；
   - 缺陷：WebSearch 的"HTTP 200"结论会被验证码页/降级页骗过 → **体检说 ✅，采集
     仍可能空手而归**；且多渠道串行探测，选 4 个渠道时可能卡十几秒。
2. **一键探针 WebSearch（360/bing/夸克）**（`main.py` 约 L1340 →
   `websearch.probe_engines`）
   - 只覆盖 WebSearch 三引擎；每次 3 个真实请求 + 解析 + 质量校验 + 风控识别，
     10~30 秒；
   - 缺陷：与体检割裂（两个按钮、两套表格/文案）；探针用 `subject+评价`，体检
     用 `test`，口径不一致。

另外，两个功能都没有回答用户真正关心的第三个维度：**这个渠道是不是被系统暂停 /
冷却中 / 当日配额用完了**（数据在 `jobs.channel_state` / `jobs.check_channel_allowed`，
现成但没接进来）。

## 二、目标与非目标

目标：

- 一个入口、一套呈现：把两个按钮合并为「渠道诊断」面板，回答"当前已选渠道是否
  正常有效"（含系统侧暂停/冷却/配额）；
- 体检结论不再骗人：WebSearch 行升级为"真实出数探测"（含风控/降级识别），而非
  HTTP 200；
- 深度探针保留但按需触发（避免每次体检都打 3 个引擎、加重风控风险）。

非目标（不做）：

- 不做自动/定时体检；不做探针自动触发；
- 不合并侧边栏"渠道安全设置"区（保留现状，面板只提示跳转）；
- 不做确认页诊断摘要（可作后续小步）。

## 三、目标形态

向导③渠道选择完成后，渲染一个「🔍 渠道诊断」区：

```text
🔍 渠道诊断  [开始诊断]        （轻量层：全渠道并行，约 5~10 秒）
┌────────────┬──────────┬──────────────────────────────┬───────────────┐
│ 渠道        │ 状态      │ 说明                          │ 操作           │
├────────────┼──────────┼──────────────────────────────┼───────────────┤
│ B站         │ ✅ 可用   │ 公开搜索 API 正常               │               │
│ 微博        │ ⚠️ 凭据   │ 未配置 Cookie（需登录后粘贴）    │ 去侧边栏保存   │
│ WebSearch  │ ⚠️ 存疑   │ 主引擎可达但命中风控特征，建议深探 │ [深度探针]     │
│ 小红书      │ ✅ 环境OK │ opencli 就绪（不主动探测会话）    │               │
│ 演示数据    │ ✅ 可用   │ 无需检查                        │               │
└────────────┴──────────┴──────────────────────────────┴───────────────┘
（每行下方小字：系统状态：今日配额 12/24 · 未冷却 · 未暂停）
```

两层深度：

1. **轻量层（开始诊断）**：并行调用升级后的 `check_channel_health`（WebSearch 行 =
   单引擎 360 真实探测 + 风控/质量识别）+ 每渠道合并 `jobs.check_channel_allowed`
   的系统状态（暂停/冷却/配额）；
2. **深度层（WebSearch 行内按钮）**：点击后展开三引擎表格（复用 `probe_engines` +
   `WS_PROBE_STATUS_CN`，查询词统一为当前任务 subject + "评价"）。

状态徽标统一口径：

| 徽标 | 含义 | 组合来源 |
|---|---|---|
| ✅ 可用 | 探测通过 + 系统允许 | health ok + allowed ok |
| ⚠️ 凭据/配置 | 缺 Cookie / 缺 opencli 等 | health warn |
| ⚠️ 存疑 | 可达但风控/降级（WebSearch） | health warn + risk/degraded |
| 🔴 不可用 | 请求失败 / 风控硬命中 / 配额用尽 | health error / risk |
| ⏳ 冷却中 | 系统冷却未到点（附剩余分钟） | allowed 原因 |

## 四、改造点明细

### 1. `app/channels/health.py`

- `check_websearch` 升级：改为复用 `websearch.py` 的
  `_fetch / _parse_engine / _quality_check / _risk_info`，对 360 主引擎发 1 个真实
  请求并识别：`ok`（有结果且质量通过）/ `degraded`（有结果但与查询无关）/ `risk`
  （验证码等硬风控，**判定不可用**）/ `empty` / `error`；不再以 HTTP 200 为准。
  - 为避免循环依赖：把探测核心抽成 `websearch.lightweight_probe(query)`（单引擎、
    含风控/质量识别），health 调用它；`probe_engines` 保持三引擎深度版。
- 返回结构统一为 `{ok, level, msg, detail}`（level ∈ ok/warn/error），兼容旧调用。
- 新增 `check_channels(channels, params)`：`ThreadPoolExecutor(max_workers=4)` 并行
  探测，逐渠道回填结果并合并 `jobs.channel_state`/`check_channel_allowed`，整体
  5~10 秒内返回；demo 渠道跳过。
- 小红书维持"环境检查 + 不主动探测会话"，文案注明（登录态探测会触发验证码）。

### 2. `app/channels/websearch.py`

- 新增 `lightweight_probe(query)`：只打 360 主引擎 1 次请求，返回与 `probe_engines`
  同构的单条结果（含 status/items/message/risk），供体检复用；
- `probe_engines` 保留（深度层），行为不变；
- 探针查询词由 UI 统一传入 `subject + "评价"`（体检不再用 `test`）。

### 3. `app/main.py`（向导③渠道设置区）

- 删除原「渠道体检（只读探测）」按钮与「一键探针 WebSearch」独立按钮；
- 新增「🔍 渠道诊断」区：
  - `st.button("开始诊断")` → `health.check_channels(selected, {cookie})`；
  - 结果渲染为表格（渠道/状态/说明）+ 每行系统状态小字（配额余量/冷却剩余/
    暂停标记）；
  - WebSearch 行出现「深度探针」按钮 → 展开三引擎表格（复用现有
    `probe_engines` + `WS_PROBE_STATUS_CN`）；
  - 冷却/暂停/配额不足的行提供"去侧边栏渠道安全设置处理"的提示文案（不重复实现
    解封 UI，非目标）。
- 状态徽标映射新增 `warn`（存疑）档，扩展 `WS_PROBE_STATUS_CN` 之外的健康状态映射。

### 4. 测试

- 新增 `tests/test_health.py`（mock `requests`）：
  - HTTP 200 但页面含验证码/风控特征 → `risk`/不可用（修复"体检骗人"的核心用例）；
  - 降级页（有结果但与查询无关）→ `degraded`/warn；
  - 多渠道并行聚合 + 系统状态合并（暂停/冷却/配额）；
  - demo 渠道跳过、小红书环境检查分支。
- `tests/test_websearch_robust.py` 补 `lightweight_probe` 单测（复用现有 mock 夹具）；
- `tests/test_ui_flow.py` 冒烟：诊断面板渲染、开始诊断按钮、WebSearch 深度探针按钮
  与表格（AppTest + mock 网络）。
- 全部纳入 `run_regression.py` 白名单，全量回归绿。

## 五、验收标准

1. 一次「开始诊断」≤15 秒（4 渠道并行），每渠道给出状态徽标 + 说明 + 系统状态；
2. WebSearch 行不再出现"体检 ✅ 但采集空手"：风控/降级时至少显示"⚠️ 存疑"并提示
   深度探针；
3. 深度探针按需可用（三引擎表格，查询词 = 任务 subject + "评价"）；
4. 全量回归（含新增 test_health / probe / UI 冒烟）绿；旧按钮入口无残留引用。

## 六、实施顺序与工作量（预估）

1. `websearch.lightweight_probe` + 单测（0.5 天）——先有可复用的探测核心；
2. `health.py` 升级 + 并行 + 系统状态合并 + test_health（0.5~1 天）；
3. `main.py` 诊断面板（1 天，含 UI 冒烟）；
4. 回归 + 手工冒烟（向导③ 4 渠道全选、WebSearch 深探、冷却渠道显示）（0.5 天）。

合计约 **2.5~3 个工作日**；可分两个提交：A=探测核心+health 升级（含测试），
B=UI 面板。

## 七、风险与回退

- 网络探测在 CI/测试中全部 mock，不引入真实请求；
- 并行探测线程数上限 4，避免与采集期请求叠加（面板只在向导③使用，采集未开始）；
- 深度探针沿用"验证码即停"保护，不自动触发；
- 回退：保留 `probe_engines` 与旧 `check_channel_health` 签名兼容（仅新增返回字段），
  若面板有问题可一键回到旧双按钮（代码层面不删旧函数，只改 UI 接线）。
