## 一、问题与目标

### 1.1 背景

`is_quality_drop(reason)`（`app/core/pipeline.py:91`）是「补采触发」的决策入口，
当前用字符串前缀判定：

```python
NON_QUALITY_DROP_PREFIXES = ("重复", "超出时间范围", "广告")
return not r.startswith(NON_QUALITY_DROP_PREFIXES)
```

审计发现三个问题：

**问题 1：前缀碰撞——现存影响是「语义分类错误 + 未来消费者陷阱」，而非触发级 bug**
（已核查代码时序与真实数据）：

- 时序：加「补采一致性清洗:」前缀的 `_reconcile_channel_posts`
  （`app/core/pipeline.py:996`）在补采循环**结束后**执行；`is_quality_drop`
  唯一调用点 `:882` 在循环内部。因此这些记录在补采判定发生时**尚不存在**，
  今天不可能抬高丢弃率或触发补采；
- 数据：真实任务 4 个含此类记录，共 77 条（66「与品牌/关键词不相关」+
  11「重复（相同正文）」），全部在决策后追加，行为影响为零；
- 真实风险：① 这些记录按文案前缀被标为 quality，任何未来消费者
  （reconcile 后调用、2.2 口径接入）读到即得错误语义；② 若未来调整 reconcile
  时序或新增调用点，立即升级为触发级 bug。属**潜在隐患，应防患于未然**。

**问题 2：字符串协议无约束。** 判定依赖「原因文案的开头」，新增原因措辞稍有
变化（如「URL 已采集过」「同帖多次返回」）即绕过判定；原因文案与决策语义耦合。

**问题 3（审核新增，实质缺口）：2.2/keyword_effects 的「决策层只用质量丢弃」
承诺未实现。** `app/core/keyword_effects.py:600` 的
`effective_rate = kept / (kept + dropped_n)`，dropped_n 为全量丢弃
（含超窗/广告/重复返回），无任何按原因过滤；`tests/run_keyword_confirm.py`
（2.2 验收）直接消费该口径。采集透明度方案 §三 承诺的「2.2 验收只用质量丢弃」
实际未落地，采集层因素仍在稀释验收口径。

### 1.2 目标

- dropped 记录创建时标注结构化 `kind`，决策依据与展示文案解耦；旧数据兜底，
  修复前缀碰撞导致的语义分类错误；
- **决策口径统一**：补采触发 + 2.2/keyword_effects 有效供给率只计质量丢弃
  （kind=quality）；展示层保持全漏斗透明；
- 契约测试锁死已知原因分类 + 序列化往返 + 兜底遥测，防止未来新增原因漏标/错标。

### 1.3 审计证据（2026-08-19 已跑通）

- 34 个真实原因字符串（22 原始 + 12「补采一致性清洗:」变体）：新判定
  （kind 优先；无 kind 剥前缀 + 前缀匹配）34/34 分类正确，0 误伤；
- 真实数据：4 个任务含「补采一致性清洗:」记录共 77 条（66 不相关 + 11 重复），
  全部在补采决策后追加 → 行为影响为零，但语义分类错误需修复；
- keyword_effects：全漏斗口径含采集层因素，无质量过滤 → 2.2 决策缺口实证。

## 二、方案设计

### 2.1 dropped 记录新增 kind 字段（三值）

`kind` 取值与决策规则：

| kind | 语义 | 是否计入决策（触发补采 / 2.2 有效供给） |
|---|---|---|
| `collection` | 采集层跳过：API 同帖重复返回、超出时间范围、广告 | 否 |
| `duplicate` | 清洗层去重：跨渠道/跨源重复（相同ID/链接/标题/正文） | 否 |
| `quality` | 质量丢弃：不相关/过短/样板/官方/正文为空/人工剔除/LLM 复核 | 是 |

决策规则统一为 **`kind == "quality"`**（collection 与 duplicate 均豁免补采——
重采同一池子不会得到新样本）。

各创建点标注：

| 创建点 | 原因 | kind |
|---|---|---|
| `channels/weibo.py:320/332/352` | 重复返回（同帖）/ 广告（ad_marked）/ 超出时间范围 | collection |
| `channels/bilibili.py:250/264` | 重复返回（同帖）/ 超出时间范围 | collection |
| `channels/xiaohongshu.py:263/274` | 重复返回（同帖）/ 超出时间范围 | collection |
| `channels/xiaohongshu.py:254` | 缺少链接（无法去重/拉取详情） | **待决策**（见 2.1.1） |
| `channels/websearch.py:543` | 官网域名黑名单 | **待决策**（见 2.1.1） |
| `coding/cleaner.py` 去重分支 | 重复（相同ID/链接/标题/正文） | duplicate |
| `coding/cleaner.py` 质量分支 | 正文为空/样板/官方/过短/不相关 | quality |
| `pipeline.py:850` | LLM 相关性复核：不相关 | quality |
| `worker.py:277/288` | 人工筛选：帖子/评论不相关 | quality |
| `pipeline.py:213` 包装 | 补采一致性清洗:{reason} | 保留原 kind（包装不改语义） |

> 已核实：`cleaner.py` 的多原因拼接（`"；".join`）不存在「质量+重复」混合记录——
> 去重原因只在无其他原因时追加且为 elif 互斥链；多原因记录均为纯质量原因。

#### 2.1.1 两处待决策取值（执行前确认，未确认按推荐值）

| 创建点 | 选项 A | 选项 B | 推荐 |
|---|---|---|---|
| 官网域名黑名单 | quality：补采重跑同一查询可能翻到更多非官方内容，有信息增量空间 | collection：同一查询前列结果仍是官方域名，补采收益低 | **A（quality，与现状一致）** |
| 缺少链接（小红书） | quality：与现状一致 | collection：补采必然重返回同一条无 URL item，白跑 | **B（collection，按豁免逻辑）** |

### 2.2 is_quality_drop 判定逻辑（新版：签名拆分 + 兜底遥测）

```python
PREFIX_WRAP = "补采一致性清洗:"
NON_QUALITY_KEYS = ("重复", "超出时间范围", "广告")


def is_quality_drop(drop: dict) -> bool:
    """决策入口：结构化 kind 优先；缺失时兜底文案判定。"""
    kind = str(drop.get("kind") or "").strip()
    if kind:
        return kind == "quality"
    return _reason_is_quality(str(drop.get("reason") or ""))


def _reason_is_quality(reason: str) -> bool:
    """旧数据兜底：先剥包装前缀，再按已知采集层原因前缀判定。"""
    r = (reason or "").strip()
    if r.startswith(PREFIX_WRAP):
        r = r[len(PREFIX_WRAP):]
    if not r:
        return False
    return not r.startswith(NON_QUALITY_KEYS)
```

要点：

- 签名只收 dict，字符串路径下沉到 `_reason_is_quality`（私有，仅兜底用）；
- 调用点 `app/core/pipeline.py:882` 传整条 `d`，并在循环内统计**无 kind 记录数**；
- **兜底遥测**：任务级若出现无 kind 记录（旧任务数据或漏标），追加一条汇总
  warning（如「N 条丢弃记录缺 kind，已按文案兜底判定」），避免静默；
- 展示层（采集说明、Excel、报告）不改：reason 文案原样保留，kind 为纯新增字段，
  序列化向后兼容。

### 2.3 2.2/keyword_effects 决策口径切换

- `app/core/keyword_effects.py:600`：新增
  `quality_effective_rate = kept / (kept + quality_dropped)`，
  quality_dropped 只计 `kind == "quality"`（无 kind 时用 `_reason_is_quality` 兜底）；
- `tests/run_keyword_confirm.py`（2.2 验收）与 eval_dashboard 决策/提示改用质量口径；
- 展示页保留全漏斗 `effective_rate`（透明），新增质量口径列并标注「决策口径」；
- **前后对照验收**：对存量关键词效果数据跑新旧口径对比，确认 2.2 已生效结论
  （如微博 Phase 2 达标）不因口径切换翻转，或有明确记录说明变化原因。

### 2.4 契约测试

`tests/test_collection_transparency.py` 内新增：

1. 已知原因 → kind 全量表断言（三值；未来新增原因未进表即回归红）；
2. kind 与 reason 不一致时 kind 优先（防错标；同时断言全表一致性）；
3. 旧记录兜底：无 kind 的 34 个变体分类与修复后期望一致；
4. 多原因拼接记录（如「文本过短；与品牌/关键词不相关」）→ quality；
5. **序列化往返**：ChannelResult（含 kind）→ dict/JSON → 重建 → kind 不丢；
   覆盖 worker 快照重建（`_apply_exclusions`）与 result.json 直读路径；
6. **兜底遥测**：无 kind 记录触发计数与 warning；
7. keyword_effects：对同一任务数据，质量口径与全漏斗口径的差异断言
   （含超窗/广告/重复记录时，quality_effective_rate > effective_rate）。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 某创建点漏标 kind | 契约测试全表锁定；漏标 = 回归红 |
| kind 与 reason 语义漂移 | 测试断言全表一致性；kind 为权威，reason 仅供展示 |
| 旧任务 JSON 无 kind | 兜底（剥前缀 + 前缀匹配）+ 任务级 warning 遥测 |
| 多原因拼接误判 | 已核实不会出现「质量+重复」混合；契约测试加多原因样例 |
| 2.2 口径切换翻转已生效结论 | 步骤 9 前后对照；翻转需记录原因并评估回退 |
| 兜底遥测告警噪音 | 任务级单条汇总 warning，不逐条刷屏 |
| 序列化路径丢 kind | 契约测试 5（往返）覆盖 |
