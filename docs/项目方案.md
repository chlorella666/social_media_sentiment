## 一、产品定位

一个**小白可上手的本地 Web 应用**：用户输入品牌/产品名（或直接手输关键词），程序以向导方式逐项确认分析维度、关键词、采集渠道和时间段，随后自动完成 **采集 → 清洗 → 情感编码 → 图表 → 报告** 全流程，输出可下载的原始数据 Excel 与 HTML/Word 分析报告。

> **当前定位（2026-08-20 收敛）**：产品收敛为「单次分析工具」（作品集导向）；
> 3.1~3.4 监控/告警/对比、打包分发、网页版方案 B 不纳入当前范围。产品需求以 [PRD](PRD.md) 为准。
> **发布状态（2026-08-24）**：GitHub 公开完成——[chlorella666/social_media_sentiment](https://github.com/chlorella666/social_media_sentiment)，
> Actions 双平台绿 + Secret Scanning 无告警；商业敏感文档仅存本地 docs/private/，不入公开仓库。

核心特性：

1. **模块化维度分类（2026-08-17 定版）**：数字产品 / 有形实物 / 服务内容三模块，
   品牌名 + 模块多选（如零售商 = 有形实物 + 服务内容）实时生成分析维度；
   关键词不再按维度自动生成建议，向导只预填品牌名，由关键词策略层优化查询串。
2. **多渠道采集**：演示数据 + WebSearch/微博/知乎/B站/小红书适配器（真实渠道 V1 接入）
3. **混合情感编码**：词典规则预筛（快、零成本）→ 低置信度文本调用大模型 API 精分析
4. **深度洞察**：12 张图表各配解析文字；结论按"发现驱动"生成（结论 + 证据引用 +
   建议，叙事框架降级为归因标签）；无 LLM 时规则生成事实性发现 + 方向性提示
5. **进度透明**：可展开的任务清单，每步状态（等待/进行中/完成/跳过/失败）与进度实时可见

## 四、技术栈

| 层 | 技术 | 版本约束 |
|----|------|----------|
| 应用框架 | Streamlit | >=1.60（`width="stretch"` 新 API） |
| 数据模型 | Pydantic v2 | >=2.7 |
| 数据处理 | pandas + openpyxl | pandas>=2.2 |
| 图表 | Plotly | >=5.22（HTML 离线内嵌） |
| Word | python-docx | >=1.1 |
| 图片渲染 | kaleido | >=1.0（v1 新 API：`start_sync_server` + `calc_fig_sync`） |
| 分词 | jieba | >=0.42 |
| 词云 | wordcloud | >=1.9（需中文字体，Windows 用 msyh.ttc） |
| 网络图 | networkx | >=3.0（spring_layout） |
| HTTP | requests | >=2.31 |
| LLM | OpenAI 兼容接口（DeepSeek 实测） | 无 |

运行环境：Windows（词云字体路径为 `C:/Windows/Fonts/msyh.ttc`）、Python 3.10+（实测 3.13）。

启动：双击 `run.bat`（自动检查依赖并 `python -m streamlit run app/main.py`），浏览器访问默认 8501 端口。

### 主题与视觉（v0.6.0 起，ui-designer 定稿）

- 主题单一事实来源：`design_entries/ui-designer/design_tokens.css`（令牌）；
  `.streamlit/config.toml` 承载 Streamlit 原生主题（品牌蓝 primaryColor、灰底、
  白卡、`textColor #1A1D23`）；控件级细节由 `app/ui/global.css` 注入兜底。
- **CSS 注入约束（Streamlit 1.60 实测）**：必须 `st.markdown(<style>…</style>,
  unsafe_allow_html=True)` 且 CSS **压缩为单行**（含空行会被 markdown 管线拆成
  可见文本）；内容中不得出现字面 `</style>`（会导致 HTML 块提前闭合）；
  `st.html` 不可用（其 DOMPurify 清洗会剥离 `<style>`）。
- 语义锁定：品牌蓝只用于按钮/链接/导航/焦点；情感三色（绿/红/灰）只用于图表/
  标签/徽章；琥珀 = 数据/流程警示，与负面红严格分离；情感信息永不单靠颜色
  （✓/✗/～ 符号叠加）；悬停仅亮度/透明度变化；按钮触控目标 ≥44px、
  主按钮 ≥15px + 字重 700；数字 `tabular-nums`。

## 六、数据模型规格（Pydantic v2）

### AnalysisPlan（采集计划，向导产物）

| 字段 | 类型 | 说明 |
|------|------|------|
| subject | str | 品牌/产品名或主题 |
| domain_id | str? | 领域 id（game/consumer） |
| dimensions | list[str] | 选中维度 id |
| keyword_groups | list[KeywordGroup] | 按维度分组关键词（dimension_id/name/keywords） |
| keywords | list[str] | 平铺关键词（采集用） |
| channels | list[ChannelConfig] | channel_id + params（如 weibo.cookie） |
| date_start/date_end | date? | 时间段 |
| per_keyword_limit | int=50 | 每关键词上限 |
| comments_enabled / comments_per_post | bool=on / int=10 | 评论开关与上限（滑块 0-10；WebSearch 摘要供给渠道不支持评论抓取，2026-08-20 spike 收口） |
| llm_enabled / narrative_enabled | bool | LLM 精分析 / 叙事归因开关 |

### Post（统一帖子模型）

`id, platform, keyword, author, title, content, url, timestamp, likes, reposts, comments_count, comments[]`，`platform_specific: dict` 存平台特有字段。

评论 `Comment`：`author, text, likes, time, is_reply, reply_to, depth`。

### CodedItem（每条文本编码结果）

`text_id, text, platform, pub_date, dimensions[], sentiment(positive/negative/neutral), intensity(1-5), sentiment_score(-1~1), confidence(0-1), method(lexicon/llm), keywords[], narrative?, attribution?`

### ReportBundle（一次分析完整结果）

`plan, channel_results[], coded_items[], summary(dict), report_text(概览), chart_insights(dict: 12 图解析), conclusion(深度结论), warnings[], created_at`

2026-08-18 起新增（均可空，旧报告降级显示）：
`findings[](发现：id/claim/evidence_refs/action/narrative_label)`、
`evidence[](证据卡：原文/平台/日期/关键词/维度/n/判定来源 llm|lexicon)`、
`insight_mode(llm|lexicon|template_fallback|no_data)`。

### summary 结构（build_summary 产出，供图表/报告/Excel 复用）

- `total_items / total_posts / avg_score / overall_sentiment`
- `sentiment_distribution`：positive/negative/neutral 的 count + ratio
- `platforms`：每平台 posts/avg_score/positive/negative/neutral
- `dimensions`：每维度 count/negative/negative_rate/avg_score
- `intensity_distribution`：1~5 级计数
- `platform_dim`：平台 × 维度 {count, negative, negative_rate}
- `date_dim`：日期 × 维度 {count, negative, negative_rate}
- `trend`：日期 {count, avg_score, negative}
- `top_words`（词典情感词 Top20）、`top_content_words`（jieba 内容词 Top50）
- `cooccurrence`：[{source, target, weight}] Top30

2026-08-18 起新增（关键词优化与报告质量提升专项 Phase 0）：
- `consumer_voice`：`{collected(采集量 N), effective(E=保留且非广告/官方),
  ratio(E/N), tier(充足/够用/不足), positive, negative, tier_channel,
  tier_ratios}`——分档正/负最小条数 = 比率×E（默认 0.1，
  bilibili/demo 为 0.05，按渠道语体参数化）；结果页展示「消费者声音占比」。

## 七、向导界面规格（app/main.py）

六阶段，用 `st.session_state["stage"]` 驱动，顶部显示步骤进度：

| 阶段 | 内容 | 关键技术点 |
|------|------|-----------|
| ① 品牌和分析维度确认 | 品牌名输入 + **模块多选**（数字产品/有形实物/服务内容）→ 维度实时预览（checkbox 默认全选、**组合强制 ≤10**）+ **自定义维度（2.8 参与统计）** | 模块变化即重算维度（composer.compose_schema）；确认时按选中维度物化 `modules_*.json`；自定义维度解析「维度名：关键词1,…」（≤4 个/≤8 字/2~5 词）且**强制全量 LLM**（无 Key 降级+提示）；不选模块 = 整体情感分析 |
| ② 关键词确认 | 可编辑 text_area（**只预填品牌名**）+ 风控提示 + 指向③的优化提示 | 不再按维度展示建议词；实际查询串由 keyword_strategy 优化（2.2）；关键词优化开关与进阶入口在③「渠道/时间」页 |
| ③ 渠道与时间 | multiselect 渠道 + date_input 范围 + 微博 Cookie 输入（可加密保存）+ **渠道诊断紧随渠道多选** + **每关键词采集条数上限（按渠道）** + **⚙️ 关键词优化模块**（WebSearch 开关 + 其他渠道开关 + 🔑 进阶入口）+ **WebSearch 采集设置**（官方域名排除）+ 词云排除词 + 广告/官方与人工复核；渠道风控安全（每日配额）移至侧边栏高级选项 | 渠道列表带适用性说明；每帖评论上限滑块 **0-10**；「抓取评论」仅对 B站/微博/小红书/演示数据生效（WebSearch 摘要供给，tooltip 已提示）；显示预计采集量与耗时；深链 `?tab=strategy` 自动拉起 8502 |
| ④ 确认运行 | 计划摘要表（模块/维度数/关键词数/渠道…）+ 关键词清单 + 启动 | 运行中：整体进度条 + st.status 内 6 步任务清单；LLM 启用时显示预计费用（展开见计算方式）与耗时说明 |
| ⑤ 后台执行 | 任务轮询页（后台队列） | 关页面不中断；任务中心可回看/重跑 |
| ⑥ 结果 | **结论优先首屏**：一句话结论胶囊（可信度/渠道/时间窗/待复核）→ 4 指标卡（整体倾向标签/平均情感分/负面占比/消费者声音）→ 整体情感主图唯一默认展开 → "只看结论/全部图表"视图切换 + 其余图折叠钻取 → 深度结论 → 下载区 | 情感标签三件套（✓/✗/～ + 色点 + 文字）；数字 tabular-nums；Excel/HTML/JSON 即时下载；Word 按需生成（按钮+spinner） |

侧边栏：**LLM 精分析开关先行**（开启后才显示 API Key 输入 + 小白获取指引 + 服务商预设/
Base URL/模型名/"🔌 测试连接"）；高级选项（默认收起）= 渠道风控安全（每日配额）+
叙事框架/归因分析；《使用边界》/数据管理/任务中心；版本号。LLM 相关性复核自 2.8 起
随 LLM 自动开启，无独立开关。

顶部步骤条：6 步线性 **SVG 图标 + 语义色**（已完成绿 / 当前品牌蓝 / 未完成灰），
执行页步骤状态 pending 灰 / running 蓝 / done 绿 / skipped 灰降透明 / failed 红。

### 关键 UI 技术点

- **预设联动**：selectbox 变更 → 写 session_state.base_url/model_name → `st.rerun()`；text_input 用 key 读取 session_state
- **模块 → 维度实时预览**：模块 multiselect 变化 → `compose_schema()` 重算维度并集
  （组合去重、>10 显示阻塞提示）；物化时机 = ① 确认"下一步"时
  （单用户桌面串行，无并发竞态），worker 按 domain_id 从缓存加载
- **任务清单实时更新**：`st.status(expanded=True)` 内预创建 6 个 `st.progress(0, text=...)` 槽位；`on_progress` 回调里逐个 `slot.progress(frac, text=f"{icon} {label}：{detail}")`
- **进度钳制**：`min(max(overall,0),1)`，防止越界（曾出现 150% bug，根因：阶段结束值被误当跨度）
- **Word 按需生成**：run 结束只生成 Excel/HTML；Word 在结果页点击后 `build_word()` 并存入 session_state 再 rerun

### 侧边栏高级设置说明（叙事框架 / 归因分析，默认关）

用户可见开关，回答"这次讨论在讲什么、把责任归给谁"：

- **叙事框架**（每条 LLM 精分析文本一个，Semetko & Valkenburg 五框架）：
  conflict 冲突 / human_interest 人情味 / attribution 归因 /
  economic 经济后果 / morality 道德；
- **责任归因**（八类）：government 政府 / enterprise 企业 / individual 个人 /
  system 制度 / technology 技术 / society 社会 / nature 自然 / unclear 不明确。

**开关区别**：关（默认）= 只做整条情感 + 维度统计 + 图表，深度结论基于图表统计生成，
费用低；开 = 对每条 LLM 精分析过的文本额外调用一次叙事/归因分析，Excel 明细多
「叙事框架」「归因主体」两列，HTML/结果 JSON 带对应字段，深度结论纳入叙事/归因结构，

**适用场景**：品牌危机 / 热点事件复盘（判断舆论责任归因与主流叙事）时开启；
日常口碑监控与新品评估通常关闭。**前置与降级**：只对 method=="llm" 的文本生效
（控制成本）；未配置 API Key 或 LLM 连接失败时自动跳过（任务步骤标记 skipped），
不报错；词典模式（LLM 关闭）下不产生标注。技术实现见 §十「LLM 分析器·职责 2」。

## 十、清洗与编码管道

### 清洗（cleaner.py）

步骤化管道（可注册增删）：

1. Unicode NFKC 规范化
2. 去 HTML 标签、URL、@提及
3. 噪声词过滤（哈哈哈/233/666 等正则）
4. 重复标点压缩（`([。！？!?~～，,.])\1+` → `\1`）
5. 空白合并

### 词典预筛（lexicon.py）——核心算法

内置词典：正词 41 个、负词 41 个、程度副词（权重表）、否定词 14 个、负面强化词 8 个（塌房/翻车/暴雷/智商税/割韭菜/逼氪/欺诈/事故，触发直接 -1.2）。

评分算法：

```
对每个命中词：
  前 2 字符窗口匹配程度副词 → degree（极2.5/太2.2/超级2.2/非常2.0/很2.0/十分2.0/特别2.0/相当2.0/比较1.3/挺1.3/蛮1.3/有点0.8/稍微0.8/略0.8）
  前 2 字符匹配否定词 → 极性翻转（×-0.8）
  正词 += 0.5 × degree × (negated?-0.8:1)
  负词 -= 0.5 × degree × (negated?-0.8:1)
score = tanh(|total|/3) 按符号
标签：score>0.15 正面；<-0.15 负面；否则中性
置信度：|score|≥0.15 → min(|score|×2.5, 1)；否则 max(1-|score|×3, 0)
无任何命中 → confidence = min(confidence, 0.2)（交给 LLM）
```

### LLM 分析器（llm_analyzer.py）——三大职责

**配置**：`LLMConfig(api_key, base_url, model)`；默认 `https://api.deepseek.com` + `deepseek-chat`（预设）。未配 Key 自动降级 `MockAnalyzer`（词典）。

**职责 1：情感精分析（analyze_batch）**

- 批量：10 条/请求，最多 4 并发（ThreadPoolExecutor），内存缓存去重
- 系统提示词（PROMPT_VERSION=12，v3.6）：返回 `{"items":[{...,"dimension_sentiments":{"维度id":"positive|negative"}}]}`，
  整条情感规则 + 维度级情感（2.4，prompt 内传入选中维度 id/名称/关键词/描述）+ 版本化
  规则开关（v3.4 SMS_V34_RULES / v3.5 / v3.6 规则 18 实物隐晦负面 few-shot）
- **路由（2026-08-17）**：`is_always_llm_domain()`——digital3c/game/consumer 与全部
  `modules_*` 合成领域**全量送 LLM**（词典只做预筛；3C 校准 spike：直判置信度不可信，
  错误率 49%）；**2.8 起（2026-08-18）`llm_enabled` 或含自定义维度也全量送 LLM**
  （未选模块/手动路径且 LLM 关闭时仍用阈值 0.8）
- **subject 口径**：`uses_subject_domain()`——digital3c 与 modules_physical/service
  （品牌口碑场景）传 subject，整条情感锚定品牌；modules_content 与 game/consumer
  走文本自身情感（抽样规范 §十四）
- 批次失败 → 词典兜底 + 记录 `errors`（结果页展示"LLM 提示"）

**职责 2：叙事/归因（analyze_narrative）**

- 10 条/批并发；`max_tokens=min(1500, 120+60×n)`
- 五框架：conflict/human_interest/attribution/economic/morality；八归因：government/enterprise/individual/system/technology/society/nature/unclear
- **取值清洗**（`_sanitize_narrative_items`）：非法值（如模型把 unclear 误填进 narrative）自动置 None 并记录错误，绝不抛异常（曾因此崩溃，回归测试覆盖）

**职责 3：深度洞察（generate_insights）**

- 输入 12 图的中文统计描述，要求输出 `{"chart_insights":{12个key的解析},"conclusion":"300~500字按五叙事框架的结论"}`，`max_tokens=3500`、超时 120s
- 失败 → 模板洞察兜底

### 编码编排（coder.py）

```
每帖：正文清洗 → 词典预筛 → 维度标签匹配（schema 关键词 contains）
  全量 LLM（digital3c/game/consumer/modules_* / llm_enabled / 含自定义维度）
  或置信度<0.8 → 标记待 LLM
每评论：同上
→ 待 LLM 文本一次性 analyze_batch（内部并发）
→ [可选] method=="llm" 的文本做叙事/归因
```

要点：`method` 标签反映真实来源（LLM 不可用时即使开关开着也只标 lexicon）；叙事分析只对 LLM 精分析过的文本执行（控制成本）；强度 `intensity = min(max(int(|score|×5)+1,1),5)`；
2.11 需复核（need_review v3）：词典直判必标 + 低置信/反讽/黑话信号，人工复核回填后
报告注明口径；词典预筛置信度封顶 0.6 展示（display_confidence）。

### jieba 分词（tokenizer.py）

- 环节：编码完成后的**文本统计环节**
- `segment()`：`jieba.lcut` → 过滤单字/纯数字/无中文/停用词（约 200+ 词，含虚词如"看看/确实/越来越"）
- `build_word_freq`：内容词 Top50 → 词云 + 内容高频词
- `build_cooccurrence`：句子窗口 3 词内词对共现，Top30 → 共现网络图

## 十一、洞察与结论生成（insights.py）

### 图表描述（build_descriptors）

把 summary 数字转中文描述，12 个 key：overall/platform/trend/dimensions/heatmap/words/intensity/radar/platform_dim/date_dim/wordcloud/cooccurrence。示例：

- overall："共编码 N 条…正面 x 条（y%）、负面…平均情感分 a，整体倾向…"
- trend：前半段 vs 后半段均分 → 上升/下降/平稳；讨论高峰日；负面峰值日
- platform_dim：每平台负面率最高维度
- date_dim：负面率最高的前 3 个 日期×维度

### 证据层（evidence.py，2026-08-18 方案）

规则抽取、确定性可回归：证据级联 = LLM 维度情感 → 词典维度情感
（match_dimension_sentiments）→ 整条情感×维度关键词 → 话题词反查 →
整体负面文本 TOP；降噪（脏话过滤 / PII 脱敏 / 截断 ≤80 字 / need_review 剔除或
标注）；守卫（n<3 不评级、零数据短路、广告剔除）。LLM 只解读给定证据，不选材。

### 模板洞察（template_insights，兜底）

每图 2~4 句数字驱动解析；2026-08-18 起兜底结论**数据化**：规则生成事实性发现
（真实 worst_dim + n + top 负面词）+ 方向性提示，不再输出静态"整体舆论以中性/正面
为主"；无 LLM 模式（MockAnalyzer）直接走此规则内核（保留方向性提示，不给出强动作
建议）；`insight_mode` 标注兜底来源。

### LLM 深度结论（generate_insights）

见 §十 职责 3。LLM 可用时优先；2026-08-18 起改为**发现驱动**：输入含证据清单，
输出 `{findings:[{id, claim, evidence_refs, action, narrative_label}]}`，
每条建议含动作/对象/渠道并挂发现编号；五框架降级为标签；失败 → 规则 findings
兜底；零数据短路不调用。详见 [报告证据链优化方案.md](archive/报告证据链优化方案.md)。

## 十三、进度与异常处理

### 阶段权重（pipeline.py）

collecting 0.0~0.5 → cleaning 0.5~0.6 → coding 0.6~0.9（词典预筛 0.6~0.75、LLM 0.75~0.9，叙事启用时 LLM 0.75~0.825、叙事 0.825~0.9）→ reporting 0.9~1.0。

### 任务清单（progress.py）

6 步：采集/清洗/词典预筛/LLM 精分析/叙事归因/生成报告，每步 state(pending/running/done/skipped/failed) + detail + frac。LLM 未启用 → skipped；无 Key → skipped(未配置 API Key)；连接失败 → failed(已降级词典)。

### 异常处理

| 场景 | 处理 |
|------|------|
| 单渠道失败 | degraded 降级，保留已采数据，继续 |
| Cookie 缺失/过期 | 降级 + warnings 提示"需要 Cookie/更新认证" |
| LLM 连接失败 | ping 自检失败 → 自动换 Mock + 警告 |
| LLM 批次失败/非法值 | 词典兜底 + errors 记录 + 清洗，不中断 |
| 样本不足 | 质量门控：<10/<30/<45/<100 逐级降级提示 |
| 用户取消 | 后台队列：排队中直接取消；运行中 request_cancel → worker 置 cancel_event，采集阶段立即停，其余阶段跑完当前批次后按取消处理（不落输出） |

### 后台任务队列（1.1，SQLite + 常驻进程）

架构：向导只负责**提交与轮询**，任务执行权在独立常驻进程（`app/worker.py`，
`run.bat` 用 pythonw 无窗口启动，`stop_worker.bat` 停止）。

- 存储：`data/app.db`（SQLite，WAL 模式支持 UI 读 + worker 写并发），
  表 `tasks`（id/type/status/subject/plan/progress_frac/message/step_snapshot/
  worker_id/heartbeat_at/cancel_requested/output_dir/result_summary/llm_usage/
  warnings/error/时间戳）+ `worker_heartbeats`；
- 状态机：pending → running → completed / failed / cancelled；
  原子抢单（UPDATE … RETURNING），多 worker 不重复执行；单任务顺序执行；
- 进度：回调节流写库（阶段切换必写 + 每 1 秒最多一次），任务级与进程级心跳各 10 秒；
- 崩溃恢复：worker 启动时把 heartbeat 超时（90s）的 running 任务标记 failed
  （可重跑，不自动重试，防重复扣费）；
- 安全：计划落库与结果 JSON 均剥离 cookie（提交前 sanitize，执行时从 DPAPI secrets
  恢复微博 Cookie）；API Key 以 Windows DPAPI 加密存本机，worker 运行时解密读取，
  永不落库（1.5：应用链路不再读明文文件/环境变量）；
- 结果索引：worker 落盘 `data/reports/<时间戳>/`（result.xlsx / report.html /
  result.json 完整 bundle），任务行存摘要指标供列表渲染；1.2 历史回看在此基础上实现。

### 结构化日志与错误排查（1.3）

目标：任何失败都能定位"哪一步、为什么、怎么办"。

- 双通道日志：SQLite `task_logs`（ts/level/step/event/message/detail，供 UI 错误视图，
  删除任务级联清理）+ JSONL `data/logs/app.jsonl`（5MB×3 轮转，本地排障，不随任务删除）；
- 事件覆盖：任务开始/阶段切换/步骤失败/执行异常/取消/渠道降级 warning/完成；
- `failed_step` 落库（含老库自动迁移），worker 崩溃恢复标记 `worker`（后台进程中断）；
- 错误建议 `app/core/errors.py`：规则映射分类（cookie/llm/ratelimit/no_data/worker/output/
  degraded）与建议分层，判定层可被 1.4 实时风控复用；措辞统一"可能原因/建议尝试"，
  无命中给兜底建议（查日志 + 一键重跑）；
- 日志健壮性：worker 日志写入 best-effort（日志故障不影响任务执行）；
  message ≤500 字符、detail ≤2000，URL/@提及/手机号脱敏（隐私口径与 1.5 一致）；
- UI：失败页（失败步骤+建议+日志）、任务详情（日志流+折叠"如何解决"）、
  结果页（仅存在 WARNING/ERROR 时折叠展示建议与日志）；
- 长期保留策略（条数/天数上限）归 1.7 数据生命周期。

### 渠道安全与配额（1.4）

目标：把"防封号"从提交前提醒升级为执行期硬机制。

- `channel_state` 表：每日配额（quota_used/quota_limit，-1=不限）、
  paused（手动暂停）、cool_until/backoff_level/last_error（风控冷却）；
  默认上限微博 200、小红书 100，其余渠道不限（可在设置区改）；
- 配额口径：按"预计采集条数 = 关键词数 × 渠道上限"计，与 UI 估算一致；
  **预扣 + 全路径校正**——完成且 ok 按实际回填、渠道失败退款、任务取消/异常退款、
  跨日重置钳 0；
- worker 执行期拦截：任务开始前预检每个渠道（暂停/冷却/配额不足 → 跳过并记
  channel_skipped 事件）；全部渠道不可用 → 任务失败（failed_step=collect，
  原因逐渠道列出，不空跑）；风控信号（errors.is_ratelimit 判定 + 渠道失败双条件）
  → 自动冷却（10→20→40→60 分钟封顶）+ cooldown 事件；
- UI：阶段3 渠道安全设置区（状态/每日上限/暂停恢复/解除冷却）、
  阶段4 提交前拦截、阶段5 运行中实时风控提示（cooldown 事件）；
- 范围边界：不涉及 Cookie/凭据（1.5）；不建配额历史表（1.7 不管）。
