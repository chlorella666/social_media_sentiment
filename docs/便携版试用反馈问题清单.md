## 详细分析

### F-001 启动后黑窗停顿 / 浏览器未自动打开

- **问题描述**：双击「启动应用.bat」后黑窗停顿，需按回车才唤醒浏览器；浏览器未自动打开。
- **根因分析（已确认，2026-08-26 DL 补充黑窗截图文字）**：黑窗实际停在 **Streamlit 首次运行的 Email 订阅提示**上（`Email: [_]` 等待输入/回车）。streamlit `config.py` 中 `server.showEmailPrompt` 默认 `True`，首次运行会在终端询问邮箱，**不回车就不会继续、浏览器也不会打开**；回车（留空）后才会启动并自动开浏览器。与端口占用/pause 无关。
- **迭代方案（根因已确认，可执行）**：
  1. 包内 `.streamlit/config.toml` 增加 `[server] showEmailPrompt = false`，从源头关闭首次邮箱提示（本地版 run.bat 同样受益）；
  2. 启动脚本给 streamlit 行追加 `<nul` 兜底（即使提示被触发也不会阻塞）；
  3. 使用说明 FAQ 加一条：“首次启动若黑窗出现 Email 提示，直接回车即可（后续版本已默认关闭）”。
- **状态**：已分析（待截图/日志 → 待执行）。

### F-003 微博 Cookie 获取指引不清晰（纯小白困扰）

### F-004 任务排队 3 分钟未执行，点「启动后台进程」后立即出报告

- **问题描述**：提交后后台执行页长时间“排队”，手动点「🔄 启动后台进程」后任务立刻执行并出报告。
- **根因分析（用户确认 + 截图已识读 2026-08-26；DL 已删文件，日志不可得，无法继续定位具体触发原因）**：直接原因 = **worker 未自动运行**；image2 铁证：结果页显示“⚠️ 后台执行进程未运行：新任务将排队等待…”+“排队中 (0%·-)”。候选原因：`pythonw` 被安全软件/SmartScreen 拦截、worker 启动即退出（pidfile/心跳互斥误判）、`start` 启动失败、或首启编译过慢（F-008）。**方案调整为“自检+留痕”：下一版启动脚本自带 worker 自检并把失败原因写入 `data/logs/launcher.log`，下次测试者遇到即可自动取证，无需回传判断。**
- **迭代方案**：
  1. 启动脚本增加 **worker 自检与自愈提示**：启动后 2~3 秒检查 `data/worker.pid` 存在且进程存活；失败时黑窗明确输出“后台进程未启动 + 可能原因 + 下一步（点应用内「启动后台进程」/ 手动运行 runtime\pythonw.exe app\worker.py 查看报错）”，并把失败信息写入 `data/logs/launcher.log`；
  2. worker 增加启动失败原因落盘：即使 pythonw 无声崩溃，下次 UI/日志可查；
  3. 包内验证 worker 心跳链路（worker → app.db → active_workers）；
  4. 保留现有「启动后台进程」兜底按钮（已确认生效）。
- **状态**：已分析（直接原因已确认；具体触发原因证据不可得（DL 已删文件）→ 以“自检+留痕”方案兜底 → 待执行）。

### F-005 报告页面首次无法浏览到底部（刷新后正常）

- **问题描述（DL 补充 2026-08-26）**：首次打开结果页/报告无法滚动到底部，需缩小页面百分比；**刷新后即可正常滚动**。
- **根因分析（确认，截图已识读）**：刷新即恢复是决定性证据；两张桌面截图显示均为**应用结果页**（含“✨ 重新生成 LLM 深度结论”按钮；image3 底部被遮挡、出现“已达底部无法查看未完内容”标注）。机制 = Streamlit 结果页 `st.plotly_chart(width="stretch")` 图表 iframe 高度需前端渲染后才确定，首帧页面总高偏小 → 底部内容截断/滚动不到；刷新后 iframe 高度就绪，恢复正常。（导出 HTML 的同步渲染阻塞作为同类风险顺带加固。）
- **迭代方案**：
  1. 模板端 `report.html.j2`：`html/body` 加 `overflow-y: scroll` 常驻滚动条 + 图表容器显式 `min-height`；
  2. 报告图表改**异步分片渲染**（逐个 `requestAnimationFrame` 执行 `Plotly.newPlot`），避免主线程阻塞；
  3. 应用结果页给 `st.plotly_chart` 容器固定/最小高度；
  4. 使用说明 FAQ：首次打开报告需等图表加载完（约几秒），滚不动可刷新一次。
- **状态**：已分析（待确认页面类型 + 待截图 → 待执行）。

### F-007 词典降级时 need_review 全量标记（数据侧观察）

- **问题描述**：DL 任务 `llm_enabled=True` 但 LLM 未生效（`insight_mode=lexicon`、method 全 lexicon、`llm_usage={}`），100 条编码全部 `need_review`。

### F-009 报告呈现层“断词/碎片化”（代表词与词云无法表达完整观点）

- **问题描述（DL 2026-08-26）**：① 抓取内容字段/字数少，不能完整体现具体指向以引导业务优化，如推荐维度代表词是“中好、想象、推荐”这类未达完整词句的词；② 词云同样断词句，如“XX 手机易碎屏幕、电池掉电快”才是完整表达。
- **根因分析（数据实证）**：词云/代表词走 **jieba 单词级词频**（`tokenizer.segment` 仅统计 ≥2 字单词）；小米任务数据实证：正面词云出现“想象/中好/推荐”（“比想象中好”拆碎）、“双十/当天/下单/首发”（“双十一当天首发下单”拆碎）、“质量/堪忧”“宣传/吹得/天花乱坠”分家；`top_words` 反而有“质量堪忧/后悔入手”等完整短语，口径不一致。
- **迭代方案（专项，参考 DL 提供的 CEMPRO 材料）**：
  1. 新增**短语级统计**：bigram/trigram + 频次/PMI 过滤，抽取完整短语（“屏幕易碎”“电池掉电快”）；
  2. 词云升级为**短语云**（短语以空格连接整体显示，避免再拆）；
  3. “代表词”升级为“**代表短语/观点**”（品牌/维度词 + 谓词 + 对象 模式抽取）；
  4. 呈现参考语义标签+占比的结构（如“清爽 64% / 涩感负面 41%”），保留并强化“负面原文 Top3”作为完整观点入口。
✅ **状态**：已验证（v0.1.9，2026-08-26）——短语抽取/短语云/共现网络短语化/口径统一；判例 fixture + 全量回归 38/38 + 黄金集 PASS。

### F-009 专门方案（产品经理 × 程序员双视角，2026-08-26 补充）
> 独立执行方案（已合并，2026-08-26）：[F-009-F-011专项执行方案.md](F-009-F-011专项执行方案.md)（§一）

> 覆盖 F-009 的 ① 代表词 与 ② 词云 两个子点（对应你消息中的 ②③ 断词/碎片化；若实际指代不同请指出）。

#### 产品经理视角
- **问题本质**：报告目前的“代表词/词云”是**单词级词频**统计，回答不了“用户到底在夸什么、骂什么”。实证：“比想象中好”被拆成“想象/中好/推荐”，“质量堪忧/后悔入手”拆成“质量/堪忧”“后悔/入手”；且同一报告里 `top_words` 是完整短语、词云是碎词，**口径矛盾**，用户会怀疑报告可信度。
- **用户价值 / 验收标准**：
  1. 代表词/词云能表达**完整观点短语**（“屏幕易碎”“电池掉电快”“比想象中好”），不再碎片化；
  2. 负面场景给出**可行动的指向**：维度 + 短语 + 原文佐证（负面原文 Top3 继续保留为完整观点入口）；
  3. **口径一致**：代表词/词云/明细短语共用同一短语源，消除“列表完整、词云碎片”的矛盾。
- **优先级**：一般偏上（报告核心输出物的可读性与专业度；也是 F-010 规则分析层的原料）。
- **上线批次**：与 F-010/F-011/F-012 同批（v0.1.9 专项四件套）——代表短语/观点正是“解读式分析”的输入；统一出 v0.1.9 验证。

#### 程序员视角
- **根因（数据实证已确认）**：`app/coding/tokenizer.py` 的 `segment` 仅做**单词级词频**（≥2 字单字词）；词云与 `top_words` 使用不同口径。
- **实现方案**：
  1. **短语抽取层（新增 `extract_phrases`，tokenizer/insights 内）**：
     - jieba 分词 → bigram/trigram 候选；
     - 过滤：去停用词/泛词（“的/了/很/真的”），保留含品牌或维度关键词的短语；频次 ≥ 阈值（如 ≥2）且 **PMI ≥ 2.0**，压制“想象/中好”这类高噪组合；
     - 定向模式：**品牌/维度词 + 谓词 + 对象**（“屏幕/易碎”“电池/掉电/快”）抽取代表观点候选；
  2. **词云升级为“短语云”**：以短语为整体渲染（短语内空格连接、不可再拆），字号/颜色按短语情感分加权；中文用系统字体（msyh）渲染并做显示验证；
  3. **“代表词”升级为“代表短语/观点”**：正负各 Top N 短语 + 占比，与负面原文 Top3 并列；
  4. **口径统一**：`top_words` / 词云 / 代表短语共用同一短语抽取结果；
  5. **兼容与降级**：小样本短语不足时回退单词级词频并标注“样本少，未形成短语”；现有词云图函数接口保持兼容（内部输入改短语）；
  6. **验证**：短语 fixture 单测（“比想象中好”“质量堪忧”“屏幕易碎”“电池掉电快”断言不拆散）；回归（test_tokenizer/test_report_insights/词云相关）保持绿；demo + 真实数据报告冒烟；便携包内导出链路（Excel/HTML/Word）验证短语云渲染。
- **风险与对策**：
  - 短语抽取引入噪音（乱组短语）→ PMI/频次/品牌维度词过滤 + 人工复核样例（沿用 32 条判例模式）；
  - 分词词典缺新词 → 保留 jieba 自定义词表扩展口；
  - 长短语在词云溢出 → 短语限长（≤8 字）+ 换行/缩放策略。

### F-013 「一键安装 opencli」失败：'node' 不是内部或外部命令 + EPERM 清理失败

- **问题描述（Aronid 2026-08-26）**：点击「一键安装 opencli」后 npm 安装失败。关键错误：
  - `npm error command C:\WINDOWS\system32\cmd.exe /d /s /c node scripts/postinstall.js || true; node scripts/fetch-adapters.js || true`
  - `npm error 'node' 不是内部或外部命令…`（`node` 与 `true` 各出现一次）
  - `npm warn cleanup [Error: EPERM: operation not permitted, rmdir 'C:\Users\Aronid\AppData\Roaming\npm\node_modules\@jackwener\opencli\node_modules\@mixmark-io\domino\test']`
- **根因分析（已确认）**：winget 刚装好 Node.js 时，新 PATH 只写入注册表，**当前应用进程及子进程仍是旧 PATH**；应用通过常见路径回退（`C:/Program Files/nodejs/npm.cmd`）找到 npm，npm.cmd 靠自身相对路径启动 npm 本体（能跑），但 opencli 包的 postinstall 由 `cmd.exe /d /s /c` 启动子进程，继承旧 PATH → `node` 找不到 → postinstall 失败 → npm 判定安装失败并回滚 → 回滚删 `@mixmark-io/domino/test` 时被 Windows Defender 实时扫描锁定/权限不足 → `EPERM`（次生错误，非主因）。附加：postinstall 的 `|| true` 是 Unix 写法，Windows cmd 无 `true` 命令，也会报错（opencli 包兼容缺陷）。
- **迭代方案（待主对话确认后执行）**：
  1. 应用侧：`install_opencli` 启动 npm 子进程时显式注入 Node 目录到 PATH（npm 所在目录 + 读注册表 HKCU/HKLM 最新 Path 合并），覆盖“winget 装完未刷新 PATH”场景；
  2. 失败分类：识别输出含 `'node' 不是内部或外部命令` → 提示“Node.js 已安装但 PATH 未刷新：请重启应用后再安装 opencli”；
  3. 残留清理：失败后检测 `%AppData%\npm\node_modules\@jackwener\opencli` 残留并提示删除/一键清理；EPERM 时提示临时关闭杀软实时防护或稍后重试；
  4. 包侧反馈（可选）：向 opencli 反馈 postinstall `|| true` 改 Windows 兼容写法（如 `|| exit /b 0`）。
- **临时恢复（用户侧）**：完全退出并重启应用让新 PATH 生效 → cmd 验证 `node --version` → 删除残留目录 → 重试安装；仍 EPERM 则临时关闭杀软实时防护或以管理员运行。
✅ **状态**：已验证（v0.1.10，2026-08-26）——Node 目录注入子进程 PATH（npm 所在目录+候选+注册表 HKCU/HKLM）+ 失败分类（PATH 未刷新/EPERM 残留）+ 残留检测提示；test_health 单测 + 全量回归 38/38 + 包内验证。

### F-015 F-009 二期：按传统访谈分析 7 步框架升级为「主题洞察」

- **问题描述（2026-08-26 产品方）**：F-009 短语化后用户感知差——demo/真实数据热门短语占比仅 1.3%~3%，且上榜短语混入「情况下/不知道/2026年/小时后评价总时长」等碎片。核心判断：当前实现等于把传统访谈分析第 1 步产物（逐字稿摘录=原始短语）直接当第 7 步结论（洞察）展示，中间缺「编码归并 → 主题提炼 → 优先级判断」，导致用户看到的是未加工原料而非分析师结论。
- **方法论映射（传统访谈分析 7 步 ↔ 产品现状 ↔ 改进方向）**：

| 步骤 | 产品现状 | 缺口 | 改进建议 |
|---|---|---|---|
| 1 编码/打标签 | 有：`extract_phrases` | 碎片多、同义未归并（电池掉电快/续航不行/耗电快=三个孤立短语） | 编码归一化：同义/近义表达映射到统一语义标签（别名表+规则） |
| 2 归类与主题提炼 | 雏形：Louvain 共现簇 | 簇只服务共现网络，未成报告主结构，簇名=原始短语 | 升级为「主题层」：簇→可读主题名，代表短语挂主题下 |
| 3 需求、痛点、期望分析 | 无 | 只说「说了什么」，不说「要什么」 | 主题下区分痛点/期望/中性诉求 |
| 4 顾客旅程/体验分析 | 部分：时间趋势、平台×维度 | 未做「主题×阶段/触点」 | 可选增强：主题×时间（新话题爆发）、主题×平台（渠道差异） |
| 5 情绪/态度分析 | 有：情感分类+短语 sentiment_weights | 未聚合为「主题级情感」 | 主题卡聚合正/负/中占比 |
| 6 量化统计与交叉分析 | 部分：维度×情感、平台×维度 | 主题层无统计 | 主题卡=提及量+正负占比+负面率+关联原文 Top3 |
| 7 洞察提炼与优先级判断 | 雏形：F-010 规则解读 | 优先级无量化排序 | 主题优先级=负面率×提及量×影响面，产出「重点问题 Top3」 |

- **三层证据结构（呈现设计）**：
  1. 主题层（给用户看）：可读名 + 一句话解读（参考 CEMPRO「清爽感以 64% 的正面评价成为最受欢迎的口味特征」）；
  2. 编码层（归并用）：归一化语义标签（如「续航差 ← 电池掉电快/续航不行/耗电快」）；
  3. 短语/原文层（证据用）：原始短语 + 关联原文 Top3 可展开（`sample_text_ids` 已有）。
  - 呈现改「主题卡」：主题名 + 提及量 + 正/负占比 + 代表短语 + 原文展开；占比分母改为所属情感子集（「占负面讨论 17%」而非「占全部 3%」）；碎片在编码层丢弃，不让用户理解原始短语。
- **工程落点**：
  1. 数据层：`extract_phrases` 后加 `encode_phrases()`（同义归一）→ `topics_from_encodes()`（复用 Louvain，节点=编码标签）；
  2. `summary` 新增 `topics` 字段 `[{name, encodes, phrases, count, sentiment_weights, sample_text_ids}]`，`top_phrases` 降级为证据层保留；
  3. 四端呈现（结果页/HTML/Excel/Word）复用 F-010 渲染管线加「主题洞察」区；旧 result.json 无 `topics` 时回退现有短语/单词不报错；
  4. 优先级算法给 F-010 用：`score = 负面率 × log(提及量) × 维度权重`，`top_issues` 输入从短语换成主题；
  5. 测试：同义归一 fixture（电池掉电快/续航不行→同一主题）、碎片过滤、主题确定性、旧数据兼容。
- **验证闭环**：5 人小样本可用性测试（对比「原始短语版 vs 主题卡版」的理解正确率与信任评分）；沿用 32 条判例模式复核「短语→编码→主题」映射，误组率 ≤10%。
- **范围控制**：先做 1（编码归一）/2（主题提炼）/3（诉求分类）/7（优先级），4（旅程）为可选增强。
- **状态**：已分析（待执行；建议作为 F-009 二期，与 F-010 联动，单独排期实现与出包）。

### F-010 LLM 接入补充项·修订（用户研究 × 产品经理 × 程序员 三视角审查，2026-08-26）

> 审查结论：方向可行，但有 4 个实质漏洞——最严重的是「让 LLM 生成数字」会同时踩中信任崩塌与内容冗余；修订为「LLM 写解读、系统填数字」的混合架构。以下 8 条问题均给出对应解决方案。

| # | 视角 | 审查问题 | 解决方案 |
|---|---|---|---|
| 1 | 用户研究 | LLM 生成数字是信任陷阱：`ratio/count` 易幻觉（34.5% 说成 45%、编造短语），用户对精确百分比信任高，错即崩塌 | 混合架构：LLM 只写解读文案（overall 措辞 / cause / direction / improvements），所有 `ratio/count/phrases` 由系统从 summary 计算填充或校验覆盖，机制上消除数字幻觉 |
| 2 | 用户研究 | 内容冗余：LLM 报告将同时出现 conclusion / findings / structured_summary 三块相似内容，认知负荷不降反升 | 定义三块定位差异：structured_summary=置顶执行摘要（速览）、findings=证据化发现（详情折叠）、conclusion=收束；呈现区分层级避免重复堆叠；5 人测试验证 structured_summary 增量价值 |
| 3 | 用户研究 | 回退分支标注不一致会误导：LLM 缺失回退规则，若仍标「LLM 判定」=造假 | 增加来源字段 `structured_summary_source: llm/rule`，四端按真实来源标注；回退时明确「规则推测」 |
| 4 | 产品经理 | 成本与价值不对等：LLM 多输出 JSON 每次耗 token，词典模式零成本 | 混合架构下 token 增量小；明确 structured_summary 在 LLM 模式=执行摘要（独立阅读价值），不做无价值的对齐 |
| 5 | 产品经理 | 「四端对齐」语义含糊：对齐布局还是字段？LLM 增量价值不明 | 明确对齐=字段契约与四端渲染一致；structured_summary 存在意义=执行摘要/速览，不是为对齐而对齐 |
| 6 | 程序员 | LLM 输出 JSON 稳定性 + token 预算：`max_tokens=4000` 已接近上限，新增嵌套结构易截断→静默回退 | 重新评估 max_tokens（预计新增 400~600 token）；输出契约紧凑，不重复 findings 内容 |
| 7 | 程序员 | 字段契约耦合：LLM 输出直接对齐内部 dict，结构一变四端模板就崩 | 定义独立「呈现契约」（JSON Schema），解析/校验/回退抽成纯函数，单测覆盖四态：解析成功/失败/字段缺失/数字越界 |
| 8 | 程序员 | 旧报告兼容：LLM 模式旧 result.json 无 structured_summary | 呈现层 `if` 兜底不渲染 + 「旧版数据」标注（F-009 G4 先例） |

**修正后实施要点（替代原补充项第 1~4 条实施要求）**

- **混合架构**：LLM 只写解读文案，`ratio/count/phrases` 由系统从 summary 计算填充（校验后覆盖 LLM 数值）；
- **三块定位**：structured_summary=置顶执行摘要、findings=证据化发现（详情折叠）、conclusion=收束；呈现区分层级；
- **来源字段**：`structured_summary_source: llm/rule`，四端按真实来源标注，回退明确「规则推测」；

- **旧报告标注**：兼容兜底 + 「旧版数据」标注；
- **用户验证**：5 人测试验证 LLM 模式 structured_summary 是否提升理解/信任，无验证不做无价值对齐。

✅ **状态（修订后）**：已验证（v0.1.11，2026-08-26）——混合架构（LLM 只写解读文案，数字由系统填充校验）；structured_summary_source llm/rule 四端标注；契约四态单测 + demo 四端渲染；LLM 缺失回退规则保证非空。

### F-008 首启依赖字节码现场编译 → 加载慢/短暂不可交互

- **问题描述**：v0.1.4 起为瘦身删除 site-packages 的 `__pycache__`/`.pyc`，首启需现场编译 streamlit/plotly/pandas 等全部依赖字节码，慢机器上可能 30~60 秒；期间页面可能处于加载/连接态，控件不可交互（疑与 F-002②、F-001“停顿”体验相关）。
- **根因分析**：删除 pyc 是体积与长路径优化的副作用；首次 import 时 Python 逐个编译 `.py`。
- **迭代方案（体积与速度权衡，需拍板）**：
  1. 构建时对 site-packages 做**预编译**（`python -m compileall`）再打包——首启秒开；体积回增约 15~30 MB（可只预编译 streamlit/plotly/pandas/numpy/matplotlib 等大头控制增幅）；
  2. 或保留精简包，但启动脚本先做一次静默预热（`python -c "import streamlit, plotly, pandas"`）再正式启动，预热窗口提示“首次启动准备中…”。
