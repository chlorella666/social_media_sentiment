## 详细分析

### F-001 启动后黑窗停顿 / 浏览器未自动打开

- **问题描述**：双击「启动应用.bat」后黑窗停顿，需按回车才唤醒浏览器；浏览器未自动打开。
- **根因分析（已确认，2026-08-26 DL 补充黑窗截图文字）**：黑窗实际停在 **Streamlit 首次运行的 Email 订阅提示**上（`Email: [_]` 等待输入/回车）。streamlit `config.py` 中 `server.showEmailPrompt` 默认 `True`，首次运行会在终端询问邮箱，**不回车就不会继续、浏览器也不会打开**；回车（留空）后才会启动并自动开浏览器。与端口占用/pause 无关。
- **迭代方案（根因已确认，可执行）**：
  1. 包内 `.streamlit/config.toml` 增加 `[server] showEmailPrompt = false`，从源头关闭首次邮箱提示（本地版 run.bat 同样受益）；
  2. 启动脚本给 streamlit 行追加 `<nul` 兜底（即使提示被触发也不会阻塞）；
  3. 使用说明 FAQ 加一条：“首次启动若黑窗出现 Email 提示，直接回车即可（后续版本已默认关闭）”。
- **状态**：已分析（待截图/日志 → 待执行）。

- **问题描述（DL 补充 2026-08-26）**：
  ① 确认页显示“《使用边界》文档缺失”（内置兜底文案）；
  ② 鼠标置于“我已阅读并同意《使用边界》”处变**禁止标志**，无法点击确认。
- **根因分析**：
  ① 文档缺失（用户确认 DL 用的 v0.1.7；**DL 已删文件，无法核验 zip SHA，2026-08-26 收口**）：最可能 = DL 拿到的是 v0.1.7 首个构建（《使用边界》误放包根目录，SHA `1726BA18…`）或旧解压目录混用；最终版 v0.1.7（SHA `1FDDB84B…`）已修且本地验证读取正常。按该假设推进，**新版本发放时附 SHA 并要求测试者核对**作为兜底。
  ② 禁止光标/无法点击（截图已识读，image1 确认复选框旁出现禁止符号）：全局 CSS 无禁用规则、结构正常；**最可能 = 首启依赖字节码现场编译期间（F-008）页面处于加载/连接态，控件暂不可交互**，光标呈禁止；刷新/加载完成后应可点击。待 DL 复测“等 1 分钟后再点”是否可点。
- **迭代方案**：
  1. 确认 DL 实际包版本：若为 v0.1.6，重新发 v0.1.7 复测；后续发放时让测试者核对 zip 名称与 SHA-256；

  3. 待截图确认是否还有元素遮挡；为首次确认页补充“加载中”状态与 UI 交互测试。
- **状态**：已分析（证据不可得：DL 已删文件，无法核验包 SHA；按假设推进 → 待执行）。

### F-003 微博 Cookie 获取指引不清晰（纯小白困扰）

- **问题描述（DL 补充 2026-08-26）**：卡在“微博 Cookie 获取指引”，现有指引对纯小白门槛高。
- **根因分析**：现有“怎么获取微博 Cookie？（小白版）”走 **Network/XHR 过滤**路径（6 步）：需理解“筛选 XHR/API 请求”“Headers → Request Headers”“截取到分号前”等概念，新手易在此卡住。已核对 `app/ui/wizard.py` 展开框文案。
- **迭代方案（采用用户提供的替代指引）**：替换为 **Application/Storage → Cookies 表** 路径（5 步）：
  1. 登录微博：电脑浏览器打开 https://m.weibo.cn 并完成登录；
  2. 打开开发者工具：按 F12，或右键页面选“检查”；
  3. 点顶部 **Application（应用程序）** 标签（某些浏览器显示“存储”/“Storage”）；
  4. 左侧展开 **Storage → Cookies**，选择 https://m.weibo.cn；
  5. 取 **SUB 对应的 VALUE 值**，填入上方微博 Cookie 文本框。
  - 补充说明：直接粘 VALUE 即可（采集器自动补 `SUB=` 前缀，已核对 weibo.py）；保留“凭证仅本机/DPAPI 加密/会过期需重取”的安全提示；
  - 同步检查 README、包内使用说明.txt 等处的微博 Cookie 指引，统一为新版。
- **状态**：已分析（待执行）。

### F-004 任务排队 3 分钟未执行，点「启动后台进程」后立即出报告

- **问题描述**：提交后后台执行页长时间“排队”，手动点「🔄 启动后台进程」后任务立刻执行并出报告。
- **根因分析（用户确认 + 截图已识读 2026-08-26；DL 已删文件，日志不可得，无法继续定位具体触发原因）**：直接原因 = **worker 未自动运行**；image2 铁证：结果页显示“⚠️ 后台执行进程未运行：新任务将排队等待…”+“排队中 (0%·-)”。候选原因：`pythonw` 被安全软件/SmartScreen 拦截、worker 启动即退出（pidfile/心跳互斥误判）、`start` 启动失败、或首启编译过慢（F-008）。**方案调整为“自检+留痕”：下一版启动脚本自带 worker 自检并把失败原因写入 `data/logs/launcher.log`，下次测试者遇到即可自动取证，无需回传判断。**
- **迭代方案**：
  1. 启动脚本增加 **worker 自检与自愈提示**：启动后 2~3 秒检查 `data/worker.pid` 存在且进程存活；失败时黑窗明确输出“后台进程未启动 + 可能原因 + 下一步（点应用内「启动后台进程」/ 手动运行 runtime\pythonw.exe app\worker.py 查看报错）”，并把失败信息写入 `data/logs/launcher.log`；
  2. worker 增加启动失败原因落盘：即使 pythonw 无声崩溃，下次 UI/日志可查；
  3. 包内验证 worker 心跳链路（worker → app.db → active_workers）；
  4. 保留现有「启动后台进程」兜底按钮（已确认生效）。
- **状态**：已分析（直接原因已确认；具体触发原因证据不可得（DL 已删文件）→ 以“自检+留痕”方案兜底 → 待执行）。

### F-005 报告页面首次无法浏览到底部（刷新后正常）

- **问题描述（DL 补充 2026-08-26）**：首次打开结果页/报告无法滚动到底部，需缩小页面百分比；**刷新后即可正常滚动**。
- **根因分析（确认，截图已识读）**：刷新即恢复是决定性证据；两张桌面截图显示均为**应用结果页**（含“✨ 重新生成 LLM 深度结论”按钮；image3 底部被遮挡、出现“已达底部无法查看未完内容”标注）。机制 = Streamlit 结果页 `st.plotly_chart(width="stretch")` 图表 iframe 高度需前端渲染后才确定，首帧页面总高偏小 → 底部内容截断/滚动不到；刷新后 iframe 高度就绪，恢复正常。（导出 HTML 的同步渲染阻塞作为同类风险顺带加固。）
- **迭代方案**：
  1. 模板端 `report.html.j2`：`html/body` 加 `overflow-y: scroll` 常驻滚动条 + 图表容器显式 `min-height`；
  2. 报告图表改**异步分片渲染**（逐个 `requestAnimationFrame` 执行 `Plotly.newPlot`），避免主线程阻塞；
  3. 应用结果页给 `st.plotly_chart` 容器固定/最小高度；
  4. 使用说明 FAQ：首次打开报告需等图表加载完（约几秒），滚不动可刷新一次。
- **状态**：已分析（待确认页面类型 + 待截图 → 待执行）。

- **状态**：已分析（待执行）。

### F-007 词典降级时 need_review 全量标记（数据侧观察）

- **问题描述**：DL 任务 `llm_enabled=True` 但 LLM 未生效（`insight_mode=lexicon`、method 全 lexicon、`llm_usage={}`），100 条编码全部 `need_review`。
- **根因分析**：① LLM 未生效 = 未配置有效 API Key（应用会提示“已开启 LLM 但未填写 API Key，将自动使用词典模式”），属配置而非崩溃；② `need_review_reason_v3(direct=True)` 对**所有**词典直判条目固定追加“词典直判(未送LLM)”→ 全量标记为需复核，属设计口径，但对无 Key 用户会造成“100 条待复核”的疲劳体验。
- **迭代方案**：① 提交/结果页对“已开 LLM 但无 Key”给出更醒目的前置提示；② 结果页需复核区区分“词典直判（未送 LLM）”与“真正低置信难例”，避免全量疲劳；③ 复核区对全量场景给说明文案。
- **状态**：已分析（待执行）。

### F-009 报告呈现层“断词/碎片化”（代表词与词云无法表达完整观点）

- **问题描述（DL 2026-08-26）**：① 抓取内容字段/字数少，不能完整体现具体指向以引导业务优化，如推荐维度代表词是“中好、想象、推荐”这类未达完整词句的词；② 词云同样断词句，如“XX 手机易碎屏幕、电池掉电快”才是完整表达。
- **根因分析（数据实证）**：词云/代表词走 **jieba 单词级词频**（`tokenizer.segment` 仅统计 ≥2 字单词）；小米任务数据实证：正面词云出现“想象/中好/推荐”（“比想象中好”拆碎）、“双十/当天/下单/首发”（“双十一当天首发下单”拆碎）、“质量/堪忧”“宣传/吹得/天花乱坠”分家；`top_words` 反而有“质量堪忧/后悔入手”等完整短语，口径不一致。
- **迭代方案（专项，参考 DL 提供的 CEMPRO 材料）**：
  1. 新增**短语级统计**：bigram/trigram + 频次/PMI 过滤，抽取完整短语（“屏幕易碎”“电池掉电快”）；
  2. 词云升级为**短语云**（短语以空格连接整体显示，避免再拆）；
  3. “代表词”升级为“**代表短语/观点**”（品牌/维度词 + 谓词 + 对象 模式抽取）；
  4. 呈现参考语义标签+占比的结构（如“清爽 64% / 涩感负面 41%”），保留并强化“负面原文 Top3”作为完整观点入口。
- **状态**：已分析（待执行）。

### F-009 专门方案（产品经理 × 程序员双视角，2026-08-26 补充）
> 独立执行方案（已合并，2026-08-26）：[F-009-F-011专项执行方案.md](F-009-F-011专项执行方案.md)（§一）

> 覆盖 F-009 的 ① 代表词 与 ② 词云 两个子点（对应你消息中的 ②③ 断词/碎片化；若实际指代不同请指出）。

#### 产品经理视角
- **问题本质**：报告目前的“代表词/词云”是**单词级词频**统计，回答不了“用户到底在夸什么、骂什么”。实证：“比想象中好”被拆成“想象/中好/推荐”，“质量堪忧/后悔入手”拆成“质量/堪忧”“后悔/入手”；且同一报告里 `top_words` 是完整短语、词云是碎词，**口径矛盾**，用户会怀疑报告可信度。
- **用户价值 / 验收标准**：
  1. 代表词/词云能表达**完整观点短语**（“屏幕易碎”“电池掉电快”“比想象中好”），不再碎片化；
  2. 负面场景给出**可行动的指向**：维度 + 短语 + 原文佐证（负面原文 Top3 继续保留为完整观点入口）；
  3. **口径一致**：代表词/词云/明细短语共用同一短语源，消除“列表完整、词云碎片”的矛盾。
- **优先级**：一般偏上（报告核心输出物的可读性与专业度；也是 F-010 规则分析层的原料）。
- **上线批次**：与 F-010（规则分析层）同批——代表短语/观点正是“解读式分析”的输入；统一出 v0.1.8 验证。

#### 程序员视角
- **根因（数据实证已确认）**：`app/coding/tokenizer.py` 的 `segment` 仅做**单词级词频**（≥2 字单字词）；词云与 `top_words` 使用不同口径。
- **实现方案**：
  1. **短语抽取层（新增 `extract_phrases`，tokenizer/insights 内）**：
     - jieba 分词 → bigram/trigram 候选；
     - 过滤：去停用词/泛词（“的/了/很/真的”），保留含品牌或维度关键词的短语；频次 ≥ 阈值（如 ≥2）且 **PMI ≥ 2.0**，压制“想象/中好”这类高噪组合；
     - 定向模式：**品牌/维度词 + 谓词 + 对象**（“屏幕/易碎”“电池/掉电/快”）抽取代表观点候选；
  2. **词云升级为“短语云”**：以短语为整体渲染（短语内空格连接、不可再拆），字号/颜色按短语情感分加权；中文用系统字体（msyh）渲染并做显示验证；
  3. **“代表词”升级为“代表短语/观点”**：正负各 Top N 短语 + 占比，与负面原文 Top3 并列；
  4. **口径统一**：`top_words` / 词云 / 代表短语共用同一短语抽取结果；
  5. **兼容与降级**：小样本短语不足时回退单词级词频并标注“样本少，未形成短语”；现有词云图函数接口保持兼容（内部输入改短语）；
  6. **验证**：短语 fixture 单测（“比想象中好”“质量堪忧”“屏幕易碎”“电池掉电快”断言不拆散）；回归（test_tokenizer/test_report_insights/词云相关）保持绿；demo + 真实数据报告冒烟；便携包内导出链路（Excel/HTML/Word）验证短语云渲染。
- **风险与对策**：
  - 短语抽取引入噪音（乱组短语）→ PMI/频次/品牌维度词过滤 + 人工复核样例（沿用 32 条判例模式）；

### F-011 凭据/关键配置输入框不显眼（全局 UX 问题：LLM API Key + 微博 Cookie）

- **问题描述（DL 2026-08-26 补充）**：API Key 文本框不显眼导致“开了 LLM 实际没用上”；此前还反馈过**微博 Cookie 输入框也不显眼、容易忽略**——判断为**全局问题**：需要用户填写的“凭据类”输入框缺少视觉引导，小白易漏填。
- **根因分析（代码确认）**：
  1. 全局无统一“待配置/必填”高亮体系：API Key、微博 Cookie 输入框与普通输入框视觉无差别；
  2. 文案弱化必要性：API Key 标“（可选）”；微博 Cookie 提示仅在②渠道页右侧栏一行，无醒目引导；
  3. 缺少“配置未完成”常驻状态提示（提交前仅一条普通 `st.warning`，易忽略）；
  4. 位置分散：API Key 在侧边栏、微博 Cookie 在向导②渠道页，用户不易形成“先配置凭据再跑”的心智。
- **迭代方案（全局统一方案）**：
  1. 建立统一**关键输入框高亮样式**：API Key、微博 Cookie 加强调边框/底色/前置图标，文案去“可选”歧义；
  2. 未配置时显示**常驻黄色状态提示条**，提交确认页用红色 error 明示对应能力将降级/不可用；
  3. 提交前“配置完整性检查”（LLM 无 Key→降级提示+去填写；微博无 Cookie→红色拦截或明确提示采集会失败）；
  4. 与 F-007/F-010 联动：词典降级与无深度分析提示统一走“配置未完成”体系。
- **状态**：已分析（待执行）。

### F-008 首启依赖字节码现场编译 → 加载慢/短暂不可交互

  2. 或保留精简包，但启动脚本先做一次静默预热（`python -c "import streamlit, plotly, pandas"`）再正式启动，预热窗口提示“首次启动准备中…”。
